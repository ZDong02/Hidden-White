# 生日礼遇功能设计方案

| 项 | 内容 |
|----|------|
| 状态 | 已实施（V1 = A+B+C，2026-11-02） |
| 日期 | 2026-11-02 |
| 关联 | 会员页 `MemberPanel.vue:107` 的静态权益卡；`docs/积分兑换方案.md`（账本与核销基础设施） |
| 依赖 | 无外部依赖；不引入定时任务（沿用「惰性结算」既有约定） |
| 涉及端 | 点单端（uni-app）、管理端（Vue3）、后端（Spring Boot）、`database/init.sql` |

## 一、背景与现状

1. **入口是假的**：`MemberPanel.vue` 的四张礼遇卡来自 `member_benefits`（会员卡背面**规则文案表**，见 `PROJECT_MAP.md:17`），点「生日礼遇」走 `openBenefit()` → `showFeature()` 弹「该会员服务当前仅展示权益说明」。除「积分兑换」外三张卡都还没有承载物。
2. **没有生日字段**：`members` 只有 `id / display_name / phone / member_level / card_number / points / coupons / growth_value`，**完全没有生日**，也没有任何"会员资料编辑"接口（`MemberController` 只有三个 GET）。
3. **优惠券没有实体**：`members.coupons` 是裸整数计数，没有券码、没有面额、没有有效期——**"发一张生日券"今天无处落地**。
4. **但账本与核销已经就绪**：`PointsLedger.adjust()` 是全应用唯一积分写入口（自增/条件扣减 + 同事务流水）；`redemptions` 表已有 8 位核销码、30 天有效期、管理端核销、惰性过期退分。生日礼遇可以直接复用这两条链路，成本很低。
5. **管理端会员编辑**只有五个字段（`Members.vue:27`：displayName / level / points / coupons / growthValue），加生日属于同一种表单扩展。

## 二、目标与范围

### 2.1 目标

- 生日礼遇从「规则文案」变成**可领取、可追溯、可运营**的真实权益；
- 会员在生日窗口内自助领取，一年一次，**绝不重复发放**；
- 运营可配置发放物、数量、窗口与文案，无需改代码；
- 每一笔发放都能在积分流水里对上账。

### 2.2 非目标（本期不做）

- 优惠券实体化（券码/面额/核销）——`coupons` 仍是计数，见 9.2；
- 自动推送（微信订阅消息）与生日关怀营销自动化；
- 按会员等级差异化发放（V2 增强，模型已留扩展位）；
- 跨店/跨品牌生日权益。

### 2.3 分期

| 阶段 | 内容 | 估时 | 备注 |
|------|------|------|------|
| **A 数据与配置** | 生日字段 + 礼遇配置表 + 管理端配置页 + 会员编辑加生日 | 0.5 天 | 前置 |
| **B 领取主链路** | 窗口判定 + 领取接口 + 账本记账 + 幂等 | 0.5 天 | 核心 |
| **C 点单端** | 生日卡四态 + 填写弹层 + 领取弹层与动效 | 0.5 天 | 面向用户 |
| **D 生日赠饮**（可选） | `gift_type=DRINK`：0 元兑换单，走既有核销 | 0.5 天 | 增强，可独立排期 |
| **E 记录与对账** | 管理端领取记录、年度统计 | 0.25 天 | — |

**V1 = A + B + C**（1.5 天，发 200 积分）；D 让「生日礼遇」真正有咖啡味，建议紧接着做。

## 三、业务规则

### 3.1 谁可以领

| 条件 | 说明 |
|------|------|
| 已登录且非游客 | 复用 `MemberSessionService.requireAccountMemberId()`，游客 → 401 引导登录 |
| 已填写生日（月、日） | 未填 → 卡片显示「填写生日，收下惊喜」，点击进填写弹层 |
| 处于礼遇窗口内 | 默认「生日当月」1 日 00:00 ~ 月末 23:59（Asia/Shanghai） |
| 当年未领过 | `member_birthday_gifts` 唯一键 `(member_id, gift_year)` |

### 3.2 窗口定义

| 模式 | 规则 | 适用 |
|------|------|------|
| `MONTH`（默认） | 生日所在自然月整月可领 | 最宽松，客诉最少 |
| `AROUND` | 生日当天 ±N 天（N 可配，默认 3） | 制造紧迫感；跨月时按自然日推算，不做月份裁剪 |

- **2 月 29 日**：平年按 **2 月 28 日** 判定（`BirthdayWindow` 内做归一，不依赖数据库）。
- 判定全部在**服务端**做，前端只展示服务端下发的 `state` 与窗口起止时间，避免机型时区差异。

### 3.3 发放物

| `gift_type` | 内容 | 落地方式 |
|-------------|------|----------|
| `POINTS`（V1 默认） | 固定积分，默认 **200**（100 积分 ≈ 3 元，约等于一杯美式的 1/3） | `PointsLedger.adjust(+N, BIRTHDAY_GIFT)` |
| `DRINK`（V2） | 一张生日专属兑换单（0 积分） | 复用 `redemptions`：`points_cost=0`，状态 `PENDING`，30 天核销，管理端用现有核销页收码 |
| `COUPON` | **暂不支持** | `members.coupons` 无实体，强行实现只会得到一个无法核销的数字 |

### 3.4 领取与幂等

- **主动领取**，不做自动发放：不引入定时任务，也不在登录时偷偷加分——用户看不见的权益等于没有。登录只做**状态判定**（惰性），与 `RedeemService.settleExpired()` 同一套思路。
- 并发/重复点击：依赖唯一索引 `(member_id, gift_year)`，捕获 `DuplicateKeyException` 后**返回已领取结果（200）**，而不是报错——用户连点两下不该看到红色提示。
- 事务：`插入领取记录 → 账本加分 → 回填 points_log_id`，任一步失败整体回滚，不会出现「记录建了积分没到」。

### 3.5 生日修改

| 规则 | 设计 |
|------|------|
| 可改频率 | **一年一次**：`members.birthday_updated_at` 距今 < 365 天则拒绝（409），文案「生日每年可修改一次」 |
| 首次填写 | 视为一次修改（防止"填错了"反复试） |
| 只收月/日 | 不采集出生年份（隐私最小化），也避开"假年份"污染数据 |
| 管理端修改 | 允许，但同样写 `birthday_updated_at`，并在操作日志留痕 |

### 3.6 降级

- 配置 `enabled = false`：卡片保留但置灰，点击提示「生日礼遇筹备中」；
- 接口异常：卡片按「非窗口期」渲染，不阻塞会员页其余内容（`Promise.all` 里做兜底）。

## 四、数据模型（写入 `database/init.sql`）

```sql
-- 1. 生日：只存月/日，不存年份
ALTER TABLE members
    ADD COLUMN birthday_month TINYINT NULL COMMENT '生日月份 1-12，NULL=未填写',
    ADD COLUMN birthday_day   TINYINT NULL COMMENT '生日日 1-31，NULL=未填写',
    ADD COLUMN birthday_updated_at DATETIME NULL COMMENT '生日最近修改时间（一年一改的判定依据）';

-- 2. 礼遇配置：单行表（id 恒为 1），运营在管理端维护
CREATE TABLE IF NOT EXISTS birthday_gift_config (
    id TINYINT UNSIGNED NOT NULL DEFAULT 1,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    gift_type VARCHAR(16) NOT NULL DEFAULT 'POINTS' COMMENT 'POINTS / DRINK',
    points_amount INT NOT NULL DEFAULT 200 COMMENT 'gift_type=POINTS 时发放积分',
    redeem_product_id VARCHAR(40) NULL COMMENT 'gift_type=DRINK 时对应的 0 元兑换品',
    window_mode VARCHAR(16) NOT NULL DEFAULT 'MONTH' COMMENT 'MONTH / AROUND',
    window_days SMALLINT NOT NULL DEFAULT 3 COMMENT 'AROUND 模式的半径天数',
    title VARCHAR(40) NOT NULL DEFAULT '生日礼遇',
    subtitle VARCHAR(60) NOT NULL DEFAULT '生日专属惊喜',
    description VARCHAR(200) NOT NULL DEFAULT '' COMMENT '领取弹层里的说明',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
) ENGINE=InnoDB COMMENT='生日礼遇配置（单行）';

-- 3. 领取记录：唯一键即幂等锁
CREATE TABLE IF NOT EXISTS member_birthday_gifts (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    member_id VARCHAR(64) NOT NULL,
    gift_year SMALLINT NOT NULL COMMENT '归属自然年，跨年重置',
    gift_type VARCHAR(16) NOT NULL,
    amount INT NOT NULL DEFAULT 0 COMMENT '积分数量或券张数',
    points_log_id BIGINT UNSIGNED NULL COMMENT '积分流水 id（gift_type=POINTS）',
    ref_id VARCHAR(64) NOT NULL DEFAULT '' COMMENT 'gift_type=DRINK 时的兑换单 id',
    created_at DATETIME(6) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_birthday_gift_member_year (member_id, gift_year),
    KEY idx_birthday_gift_year (gift_year, created_at),
    CONSTRAINT fk_birthday_gift_member FOREIGN KEY (member_id) REFERENCES members(id)
) ENGINE=InnoDB COMMENT='生日礼遇领取记录';
```

> 备选：`birthday DATE`。不采用——DATE 必须带年份，要么塞 1900 这种假数据，要么额外记录"是否公开年份"，都比三个显式列复杂。

## 五、后端设计

### 5.1 判定逻辑收在一个纯函数里

`common/birthday/BirthdayWindow`（无 Spring 依赖，可直接单测）：

```java
record Window(boolean claimable, LocalDate from, LocalDate to, int daysUntil) {}
Window of(int month, int day, LocalDate today, String mode, int radius)
```

- 2/29 → 平年归一为 2/28；
- `MONTH` 输出本月 1 日 ~ 月末；
- `AROUND` 输出 `birthday ± radius`，跨年取最近的未来一次；
- `daysUntil` 供前端显示「距离生日还有 152 天」。

### 5.2 点单端接口（`shop` 模块，需会员登录）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/members/birthday` | 配置 + 我的状态：`state`(NO_BIRTHDAY/NOT_IN_WINDOW/CLAIMABLE/CLAIMED)、`windowFrom`、`windowTo`、`daysUntil`、`claim`（已领时的年份/数量/时间） |
| PUT | `/api/members/me/birthday` | body `{month, day}`；一年一改，二次修改 409 |
| POST | `/api/members/birthday/claim` | 领取；幂等（重复请求返回 200 + 已领结果） |

`state` 由服务端算好，前端不再自行比较日期——这是「同一个月在不同时区/机型上表现不一致」的根因防线。

### 5.3 领取事务（`BirthdayGiftService.claim`）

```
1. 读配置（enabled=false → 409「礼遇筹备中」）
2. requireAccountMemberId()（游客 401）
3. 读会员生日（空 → 409「先填写生日」）
4. BirthdayWindow 判定（不在窗口 → 409 + 具体日期，前端据此渲染）
5. INSERT member_birthday_gifts（唯一键冲突 → 直接返回已领）
6. gift_type=POINTS：pointsLedger.adjust(+N, BIRTHDAY_GIFT, BIRTHDAY_GIFT, id, "生日礼遇")
   gift_type=DRINK ：建 0 元兑换单，回填 ref_id
7. 回填 points_log_id / ref_id
```

### 5.4 账本扩展

- `PointsBizType` 增加 `BIRTHDAY_GIFT`（`isSpend()` 返回 false）；
- `PointsRefType` 增加 `BIRTHDAY_GIFT`；
- 除账本外**任何地方不得直接 UPDATE `members.points`**（既有约定，见 MEMORY「积分体系约定」）。

### 5.5 管理端接口（新包 `admin/birthday/`，套路同 `admin/redeem`）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET/PUT | `/api/admin/birthday/config` | 礼遇配置读写（PUT 记 `@OperLog`） |
| GET | `/api/admin/birthday/gifts` | 领取记录（按年、按会员关键字、分页） |
| GET | `/api/admin/birthday/stats` | 本年度发放人次 / 积分合计 |

`CoffeeService.updateMember` 增加 `birthdayMonth/birthdayDay` 写入 + `birthday_updated_at`。

## 六、点单端设计（uni-app）

### 6.1 生日卡的四态

卡片沿用现有 `.benefit-card` 规格（`min-height:176rpx`、`$r-lg`、白底、浅金图标底），只按状态换层信息：

| 状态 | 图标底 | 标题 / 副标题 | 交互 |
|------|--------|---------------|------|
| `NO_BIRTHDAY` | 浅金 | 生日礼遇 / 填写生日，收下惊喜 | 打开填写弹层 |
| `NOT_IN_WINDOW` | 浅金 | 生日礼遇 / 生日月 · 每月一次 | 打开详情弹层（显示"距离生日还有 N 天"） |
| `CLAIMABLE` | 金色实底 + 呼吸点 | 生日礼遇 / 本月可领 200 积分 | 打开领取弹层，主按钮「立即领取」 |
| `CLAIMED` | 灰金 | 生日礼遇 / 已领取 · 200 积分已入账 | 打开详情（显示领取时间） |

- 只有 `CLAIMABLE` 允许出现强调色描边与角标——**一屏只有一个强调色**是本项目既有规则；
- 领取成功后卡片就地切到 `CLAIMED`，并让「当前积分」做一个数字滚动（`$dur-slow`），让"加分"这件事被看见；
- 副标题里不放日期，日期放在弹层——卡片只有 176rpx 高，塞日期会挤掉标题。

### 6.2 弹层

1. **填写生日弹层**：`<picker mode="date">` 但只取月/日（`fields="day"` 后取 `slice(5)`）；二次修改时按钮置灰并提示「生日每年可修改一次」。
2. **领取弹层**：深色卡（复用 `.card-dark`）——生日日期、礼遇内容、「立即领取」主按钮、一行小字说明。深色卡是"仪式感"的载体，与浅色的填写弹层区分开。
3. 领取中按钮 loading 且禁用（防连点），失败按 `409` 的文案原样展示。

### 6.3 数据

`MemberPanel.activate()` 里把 `/members/birthday` 并进现有 `Promise.all`，失败不影响资料与权益列表渲染：

```js
const [profile, rows, birthday] = await Promise.allSettled([...])
```

## 八、测试与验收

### 8.1 单测要点（`BirthdayWindowTest` + `BirthdayGiftServiceTest`）

- `MONTH`：月初 1 日、月末最后一天可领；前一日/后一日不可领；
- `AROUND`：生日当天可领；`±N` 边界；跨月（生日 3 月 1 日，半径 3 → 2 月 26 日起可领）；
- 2 月 29 日：闰年当天空过 → 平年 2 月 28 日可领；闰年 2 月 28 日不可领；
- 跨年：12 月 31 日生日，次年 1 月 1 日不应误判；
- 幂等：连续两次 `claim` 只产生一条记录、一次流水；
- 一年一改：第二次 `PUT` 返回 409，`birthday_updated_at` 不变。

### 8.2 验收清单

- [ ] 未填生日 → 卡片显示「填写生日」，填写后立刻变为「本月可领」；
- [ ] 领取 → 积分 +200，`member_points_log` 出现 `BIRTHDAY_GIFT` 流水，`balance_after` 与会员页显示一致；
- [ ] 连点两次「立即领取」只发一次，第二次无报错；
- [ ] 非生日月访问领取接口 → 409，文案含具体日期；
- [ ] 生日改第二次 → 409，文案「生日每年可修改一次」；
- [ ] 游客点卡片 → 引导登录，登录后回到会员页；
- [ ] 关闭配置 → 卡片置灰且点击提示「筹备中」；
- [ ] 管理端发放记录与 `member_birthday_gifts` 行数一致，年度积分合计 = 流水合计；
- [ ] 小程序端与 H5 端窗口判定一致（都以服务端 `state` 为准）。

## 九、风险与注意事项

1. **刷积分**：生日造假是最大风险。缓解 = 一年一改 + 必须登录（手机号绑定）+ 积分总额可控 + 管理端可按会员查领取记录；不建议做"身份证校验"（成本远高于收益）。
2. **券不可用**：`coupons` 无实体，V1 千万不要在文案里写"生日券"——发不出去的承诺比没有更伤。
3. **时区**：服务端用 `Asia/Shanghai` 固定时区计算窗口；不要用前端 `new Date()` 判定。
4. **管理端改积分**：`Members.vue` 现在把目标值换算成差值交给账本，加生日字段时**不要顺手把 points 改回直接赋值**。
5. **积分文案单位**：100 积分 ≈ 3 元，200 积分约等于 6 元。若运营想给"一杯免费"，应当走 `DRINK` 而不是把积分调到 600+（积分能抵现的话会打穿定价体系）。
6. **性能**：生日状态随会员页加载，属于低频小接口；配置读取加 60 秒本地缓存即可，不必上 Redis。

### 11.2 与方案的差异（实施时的判断）

1. **弹层合成一个**：方案写「填写弹层 + 领取弹层」两个，实施改为**一个弹层五种内容**。理由：用户视角只做一件事——看我的生日礼遇；两弹层来回切换会闪。状态差异在内容区消化。
2. **弹层必须在页面层**：`swiper-item` 带 transform，`position: fixed` 在微信端会相对它定位（本项目取餐凭证弹窗已有同样结论）。因此状态抽到 `store/birthday.js`，卡片与弹层共享。
3. **`gift_year` 取「生日所在年」而非领取当天年**：1 月 2 日生日的会员可能在前一年 12 月 30 日进入 AROUND 窗口，若按领取年记账会出现一年领两次。
4. **赠饮模式在配置写入处直接拒绝**：`giftType=DRINK` 需要 0 元兑换单联动，链路未通；放开只会让运营配出一个点了就报错的开关。管理端下拉里以「未开放」置灰呈现。
5. **管理端菜单挂在「咖啡运营」下（408）**：会员管理、会员权益都在 400 段，生日礼遇属于同一批运营配置，不再单开一级目录。
