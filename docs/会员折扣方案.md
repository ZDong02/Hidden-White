## 一、需求与关键决策

> 原始需求：按会员的不同等级划分折扣策略，并为每个等级配置每周不同的折扣方案。

### 1.1 「每周不同」的解读

需求里的「每周」有两种可能：**按自然周轮换**（这周 9 折、下周 8.5 折），或**按星期固定**（周三会员日 8.8 折、周末原价）。

本项目按后者实现，理由：

- 门店的折扣规律几乎都是「周几」而不是「第几周」——「本周特惠」这种玩法属于活动，不属于会员等级；
- 按自然周存方案意味着每周都要有人去配一次，或者写一套轮换规则；配一次忘一次，就会出现「本周没有任何折扣」；
- 按星期是**周期规律**，配一次长期有效，运营成本接近零。

如果将来真需要「本周特殊价」（周年庆），当前实现有两处扩展位：
`member_level_daily_rates` 加一列 `week_key`（NULL 表示不限周）即可表达「某周某天特殊」，
领域层只需在 `LevelDiscountService.rateOn` 里多查一层，不动表结构与接口形态。

### 1.2 决策表

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 等级定义 | 沿用 `MemberLevels` 的**代码阶梯**（成长值 0/500/1500/4000/10000） | 晋升规则（只升不降）已经在代码里，表里再存一份等级就有两个真源 |
| 折扣粒度 | **等级 × 星期**（7 天可各自覆盖），未配置的天继承基准 | 一份配置管长期，不用每周维护 |
| 折扣率语义 | `rate = 折后价 / 原价`，`0.850` = 8.5 折 | 所有金额计算都是乘法，少一次「8.5 ÷ 10」就少一处出错 |
| 门槛基数 | 订单**商品金额**，不含包装费 | 包装费是履约成本，不是商品价值 |
| 与首单礼遇 | **互斥，取优惠更大者** | 都是「身份让利」，叠加会让新老客价差失去意义 |
| 与优惠券 | **叠加**，券在折后金额上抵扣 | 券是营销工具，否则 8.8 折的钻石会员永远用不上券 |
| 订单明细 | 独立表 `order_discounts`，一单多行 | 加列意味着每加一种优惠就改一次 `Order` record（24 个构造参数） |
| 未知等级 | 安静地不打折 | 会员等级允许被手工改错，不该让顾客下不了单 |

## 二、等级划分

| 等级 | 起点成长值 | 默认折扣 | 说明 |
|------|-----------|----------|------|
| 普通会员 | 0 | 不参与 | 默认等级，打折等于全场降价，所以默认关闭 |
| 白银会员 | 500 | 9.7 折 | |
| 黄金会员 | 1500 | 9.5 折 | |
| 铂金会员 | 4000 | 9.2 折 | |
| 钻石会员 | 10000 | 8.8 折 | |

- 1 元 = 10 成长值、1 元 = 1 积分（`ShopRepository.awardOrderPoints`）。
- 等级**只升不降**：成长值累积到门槛即晋升，不会因为一段时间不消费而降级。
- 折扣率是初始值，运营可在管理端逐档调整；表里存的是「配置」，代码里的是「阶梯」，两者职责不重叠。

## 三、每周折扣的计算与生效规则

### 3.1 判定顺序（服务端唯一实现）

```
① 会员等级          members.member_level，且必须在阶梯内（否则视为无折扣）
② 当天折扣率        有 daily 覆盖用覆盖，否则用 base_rate
③ 是否启用          discount_enabled = true 且 rate < 1.000
④ 是否达门槛        subtotal >= min_spend
⑤ 折扣金额          subtotal × (1 - rate)，四舍五入到分
```

任一条不满足 → 本单没有会员折扣，**不报错、不提示**，账单上不出现这一行。

### 3.2 计算示例

32 元的招牌馥白，黄金会员周四（单独配了 8.5 折）：

```
subtotal = 32.00
rate     = 0.850                    ← 当天覆盖值
折扣     = 32.00 × (1 - 0.85) = 4.80
折后     = 27.20
```

### 3.3 与其它优惠的组合

| 组合 | 规则 | 32 元单的结果 |
|------|------|---------------|
| 只有会员折扣 | 直接减 | 减 4.80 → 27.20 |
| 会员折扣 + 首单礼遇 | 互斥，取大者 | 首单 6 元胜出 → 26.00 |
| 会员折扣 + 优惠券 | 叠加，券在折后抵扣 | 4.80 + 6.00 = 10.80 → 21.20 |
| 首单礼遇 + 优惠券 | 互斥，取大者 | 6 元胜出 → 26.00 |

一句话：**身份权益（首单 / 等级折扣）只能拿一个；营销权益（券）能叠在折扣上，不能叠在首单上。**

为什么券不能叠首单：首单礼遇是无门槛、与券同面额的「见面礼」，它本来就是给「还没有券可用」的新客准备的。
让它和券叠加，等于把它的定位抹掉，且新客首单会白拿双份（32 元单减 12 元）。

**券的门槛仍按原价判定**：顾客看到的是「满 20 元可用」，折后 19 元就说券失效会让人觉得被算计；
而抵扣额按折后金额截断（`min(面额, 折后金额)`），保证实付不会变成负数。

## 四、数据存储

### 4.1 三张表

```
member_level_policies      每等级一行：启用 / 基准率 / 门槛 / 说明
member_level_daily_rates   等级 × 星期 的覆盖值（只存配置过的天）
order_discounts            订单优惠明细（一单多行，含等级折扣与券）
```

### 4.2 `member_level_policies`

| 列 | 说明 |
|----|------|
| `level_key` | 主键，与 `members.member_level` 对齐（中文，如「黄金会员」） |
| `level_name` / `min_growth` | 展示快照，每次保存时由 `MemberLevels` 覆盖，避免与晋升逻辑脱节 |
| `discount_enabled` | 是否参与折扣 |
| `base_rate` | 基准折扣率，`1.000` = 不打折 |
| `min_spend` | 门槛，`0` = 无门槛 |
| `note` | 点单端展示的一句话 |
| `sort_order` | 阶梯顺序 |

### 4.3 `member_level_daily_rates`

主键 `(level_key, weekday)`，`weekday` 用 ISO 编号（1 = 周一 … 7 = 周日）。

**只存覆盖行**，不预置 7×N 行：

- 未配置的天自然回落到 `base_rate`，运营改基准价不必逐格同步；
- 矩阵页面上留空 = 继承，不会被误当成「这天不打折」；
- 想恢复继承，删掉那一格即可，不用填一个与基准相同的数字。

### 4.4 `order_discounts`

| 列 | 说明 |
|----|------|
| `type` | `LEVEL` / `FIRST_ORDER` / `COUPON`（新增优惠种类只加常量，不动表） |
| `label` | 账单文案，如「黄金会员 8.5 折」 |
| `amount` | 本项抵扣金额 |
| `ref_id` | 关联对象（券 id 等），客诉时反查 |

`orders.discount` 仍是**总优惠**（用于列表快速查询），`order_discounts` 是它的明细，
两者之和应当相等。不存明细的话，顾客问「为什么少了 10.8 元」只能靠翻配置猜。

## 五、主要接口

### 5.1 点单端（需登录）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/members/discount` | 当前等级视图：今日折扣、整周日历、距下一等级还差多少成长值（会员页折扣条用） |
| GET | `/api/members/level-discounts` | 全部等级方案：五档各自的折扣、周历、门槛、是否当前等级、是否已达成（折扣详情页用） |

两个接口分工明确：前者回答「我今天打几折」，后者回答「各档分别是什么、我还差多少」。
合成一个接口会让会员页为二级页多读 5 遍策略，而详情页又拿不到「当前在哪档」以外的横向对比。

报价与下单沿用 `POST /api/cart/quote` 与 `POST /api/orders`，**无需新增参数** ——
折扣按「当前会员 + 今天」自动生效，客户端无法指定等级或折扣率。

响应示例：

```json
{
  "levelKey": "黄金会员",
  "levelName": "黄金会员",
  "enabled": true,
  "todayRate": 0.850,
  "todayLabel": "黄金会员 8.5 折",
  "note": "全场 9.5 折",
  "minSpend": 0,
  "active": true,
  "week": [
    { "weekday": 1, "label": "周一", "rate": 0.950, "overridden": false, "today": false, "active": true }
  ],
  "nextLevel": { "name": "铂金会员", "minGrowth": 4000, "growthLeft": 2400 }
}
```

报价结果新增 `discounts` 数组（账单逐行渲染用）：

```json
{
  "subtotal": 32.00, "discount": 10.80, "packagingFee": 0, "total": 21.20, "count": 1,
  "discounts": [
    { "type": "LEVEL",  "label": "黄金会员 8.5 折", "amount": 4.80, "refId": null },
    { "type": "COUPON", "label": "每周好券",        "amount": 6.00, "refId": "9adcb62a-…" }
  ]
}
```

### 5.2 管理端

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/admin/level-discounts` | `coffee:leveldiscount:list` | 总览：每等级策略 + 成员数 + 阶梯 + 孤儿等级 |
| PUT | `/api/admin/level-discounts` | `coffee:leveldiscount:edit` | 整行保存（含每日覆盖），记操作日志 |
| PUT | `/api/admin/level-discounts/enabled` | `coffee:leveldiscount:edit` | 单字段启停，记操作日志 |

**为什么 `levelKey` 走请求体而不是路径**：等级键是中文（「白银会员」），
放进 URL 要依赖各层对编码的一致处理；放 body 里没有这个风险。

**为什么启停是独立端点**：整行更新带必填校验，会把「只想关掉」的调用拒掉
（与商品上下架、兑换品上下架同一约定）。

每日覆盖的传参是「覆盖集」：

```json
{ "levelKey": "黄金会员", "enabled": true, "baseRate": 0.95, "minSpend": 0,
  "note": "全场 9.5 折", "dailyRates": { "3": 0.88, "6": 0.92 } }
```

未出现在 `dailyRates` 里的星期 = 继承基准（服务端会删掉对应的覆盖行）。

## 六、校验处理

### 6.1 服务端（最终判定）

| 项 | 规则 | 违反时 |
|----|------|--------|
| 等级 | 必须在 `MemberLevels` 阶梯内 | 400「等级「金卡会员」不在成长值阶梯中…」 |
| 折扣率 | `0.1 ≤ rate ≤ 1.0` | 400「不能低于 0.1（1 折）；低于 1 折请走优惠券或专门活动」 |
| 折扣率 | 不能为 `null` | 400「基准折扣率不能为空」 |
| 门槛 | `≥ 0` | 400「折扣门槛不能为负数」 |
| 星期 | `1–7` | 400「星期取值不合法：9（应为 1-7，1 = 周一）」 |
| 说明 | ≤ 120 字 | 400 |
| 折扣率精度 | 统一 `setScale(3)` | 静默规整（0.8555 → 0.856） |

下限 0.1 不是业务上限，而是防误填：0.1 已经意味着 10 元的咖啡卖 1 元，
再低几乎只可能是把「8.5」写成「0.85」之类的笔误。

**为什么拒绝阶梯外等级**：这种等级永远不会被成长值晋升覆盖（`rankOf` 返回 -1），
给它配折扣等于把资损固化成配置。正确做法是先去会员管理把等级改回阶梯内。

### 6.2 前端（第一道拦截）

管理端在提交前做同一套边界校验，标红对应格子并阻止提交。
但前端只做「明显填错」的拦截 —— 折扣率多一位小数就是全体该等级会员的每一单，
服务端那道不能省。

### 6.3 运行时的容错

- 会员等级在阶梯外 → **无折扣**（不抛错，顾客照常下单）；
- 策略表为空 / 某等级没有策略行 → 无折扣，管理端仍展示该等级（按默认值）；
- `rate = 1.000` 与「关闭开关」在金额上等价，都按原价结算。

## 七、点单端展示

### 7.1 结算页账单

```
商品金额              ¥32
黄金会员 8.5 折        −¥4.80
优惠券                −¥6.00  ›
包装费                ¥0
合计                  ¥21.20
```

- 身份权益行（折扣 / 首单）由 `discounts` 逐行渲染，文案与金额都来自服务端；
- 优惠券单独一行并做成入口 —— 它是本页唯一可以更换的优惠；
- 摊不开的明细不显示总数：顾客看到「少了 10.8 元」却不知道原因，是最容易引发客诉的形态。

### 7.2 会员页

- 今天真的打折时才显示一条金色折扣条：`黄金会员 8.5 折` + 运营配的说明；
- 点击进入**会员折扣详情页**（弹窗放不下五档 × 七天的方案，一屏滚动阅读才是对的形态）；
- 今天不打折就整条不渲染：「今天原价」这种信息不占版面，反而让会员觉得自己在吃亏；
- 礼遇网格里的「会员折扣」卡片同样进入详情页（此前是一句「正在筹备中」）。

### 7.3 会员折扣详情页（`pages/level-discount/index`）

自上而下三段：

| 区块 | 内容 |
|------|------|
| 当前等级 hero | 该档卡面配色；今日折扣大字、适用范围、门槛；距下一档的成长值进度条 |
| 等级方案列表 | 一档一卡：折扣幅度（大字）、成长值门槛、适用范围、整周七天折扣 |
| 计算规则 | 服务端下发的四条规则（互斥/叠加/门槛基数/单档结算） |

设计要点：

- **今天那一格点亮**：周历七格里当天用浅金底，顾客一眼看到「今天就是这个价」；
  只显示今天会让人以为天天一样，而运营可能把周三设成会员日、周末调回原价。
- **当前等级描金边 + 「当前等级」标**，已达成的档标「已达成」，未达成的标「还差 N 成长值」并降透明度。
- **等级色只用在色条、等级名、圆点三处**（浅底卡），不铺大块色，避免五张卡并排时过重。
- 窄屏（≤340px）缩周历字号而不是换行 —— 换行会破坏「一周一排」的读法。

### 7.4 等级卡面配色

会员卡与详情页 hero 共用 `tokens.scss` 的 `$level-cards`，五档各一套：
`face-a/face-b`（渐变两端）、`glow`（左上高光）、`accent`（深底文字）、
`ink`（浅底等级色）、`line`（描边）、`muted`（次文字）、`ring`（右下装饰环）。

| 等级 | 色相 | 渐变起 → 止 | 强调色 |
|------|------|-------------|--------|
| 普通会员 | 暖褐灰 | `#232019` → `#14120e` | `#e6dfcd` 米白 |
| 白银会员 | 冷灰蓝 | `#2a2e34` → `#16191d` | `#dfe6ef` 冷银白 |
| 黄金会员 | 暖褐金 | `#2b2416` → `#16130d` | `#e9d191` 品牌金 |
| 铂金会员 | 紫灰 | `#2b2837` → `#16141f` | `#ddd5f0` 淡紫白 |
| 钻石会员 | 深靛蓝 | `#1c2436` → `#0e1119` | `#cfe0ff` 冰蓝白 |

色相走向是「暖褐 → 冷银 → 品牌金 → 紫灰 → 冰蓝」，普通最弱、钻石最冷最亮，符合等级递增的心理预期；
五档明度对齐，并排放在列表里也能一眼分出高低。

**为什么同一个等级有两个色值**（`accent` 与 `ink`）：深色卡上需要亮色、浅色卡上需要够暗的颜色，
拿一个色值硬套两种底色，必然有一边对比度不足。`ink` 专门给浅底卡的色条与等级名用。

**等级徽标改用圆点而不是图标**：`Icon` 是固定色的 PNG（只有 gold / gold-on-dark 几档），
在白银、铂金、钻石的冷色卡面上会形成脏混色；圆点用 `currentColor`，天然跟随各档强调色。

## 八、管理端功能点

**页面**：咖啡运营 → 会员折扣（菜单 410，`coffee/leveldiscount/index`）

**矩阵**（行 = 等级，列 = 周一至周日）：

| 列 | 内容 |
|----|------|
| 等级 | 等级名 + 起点成长值 |
| 成员 | 该等级会员数（判断改动影响面） |
| 启用 | 开关，立即生效（走独立端点） |
| 基准 | 折扣（8.5）+ 门槛（元） |
| 周一~周日 | 单独覆盖值，留空 = 继承基准；今天那一列有「今天」标记 |
| 保存 | 逐行保存（整行原子更新） |

**孤儿等级提示条**：会员身上出现、但不在阶梯中的等级（如被手工改成「金卡会员」）会列出来，
并提示「这些会员拿不到任何折扣，请到会员管理改回阶梯内」。不提示的话，这类会员会静默地一直原价。

**规则说明区**：把我 §3.3 的组合关系写在页面上，避免运营靠猜。

## 九、已知边界与后续

1. **不做「按自然周轮换」**：需要的不是折扣而是活动，见 §1.1 的扩展位。
2. **不做分类/单品折扣**：当前是全场。若要做「咖啡 9.5 折、周边原价」，
   `order_discounts` 已能承载明细，但折扣计算需要按分类拆行 —— 属独立议题。
3. **不做自动调整提醒**：运营把折扣率从 9.5 改成 8.5 时，页面不会提示「毛利下降 x%」。
4. **阶梯外等级只能手工修**：管理端会员编辑目前是自由文本输入等级名，是这类脏数据的源头。
   改成下拉（只能选阶梯内等级）可以根除，但会牵动会员表单，本次未做。
5. **`members.member_level` 无外键**：不指向 `member_level_policies`，因为等级是代码常量，
   表里只是策略。加外键会让「新增等级」必须同时写数据迁移。
6. **`GET /api/members/{id}` 会吞掉未定义的子路径**（2026-11-05 踩到）：
   新增 `/api/members/level-discounts` 后若后端进程没重启到最新代码，该路径会落到
   `/{id}` 上，被当成会员 ID 走归属校验，返回 **403「无权查看该会员资料」** ——
   一个把排查方向引向 token 与权限的错误答案。已在 `MemberController` 加保留字清单
   （`RESERVED_PATHS`），让这种情况返回 **404「接口不存在」**。
   新增 `/api/members/**` 子路径时要同步那份清单。
