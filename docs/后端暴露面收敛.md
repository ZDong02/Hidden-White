# 后端暴露面收敛（后端服务对外隐藏）

> 目标：客户端（点单端 H5 / 微信小程序 / 管理端）**不再知道后端在哪，也不能直连后端**。
> 公网上只有一个域名、一个 443 端口；后端只监听回环，且只接受带网关密钥的请求。

---

## 一、改造前后的拓扑

**改造前**（问题所在）

```
手机小程序 / H5 / 局域网任意设备
        │  http://10.30.x.x:8080  ← 内网 IP 硬编码在客户端配置里，端口对全网开放
        ▼
   Spring Boot（0.0.0.0:8080）
        ├── /api/**            点单接口
        ├── /api/admin/**      管理接口
        ├── /uploads/**        商品图
        └── /error、Knife4j 文档路径 …
```

**改造后**

```
客户端（只认 https://coffee.example.com）
        │  443（TLS）
        ▼
      nginx  ── /            → 点单端 H5 静态文件
             ── /admin/      → 管理端静态文件
             ── /api/        → 反代 + 注入 X-HW-Gateway + 限流
             ── /uploads/    → 反代商品图
             ── 其余路径      → 404
        │  127.0.0.1:8080（仅本机；外部连不上）
        ▼
   Spring Boot（IngressGuardFilter 先验密钥）
```

## 二、需要隐藏的服务范围

| 暴露面 | 改造前状态 | 处理方式 |
|---|---|---|
| 后端端口 `8080` | 监听 `0.0.0.0`，局域网设备可直连 | prod profile 绑定 `127.0.0.1`（`SERVER_ADDRESS` 可覆盖为内网地址，但**不允许 `0.0.0.0`**） |
| `/api/**` 点单接口 | 客户端直连，无限流、无边缘白名单 | 只经 nginx `/api/` 进入；边缘限流 300 r/min，认证入口 30 r/min |
| `/api/admin/**` 管理接口 | 与点单接口同端口暴露 | 同域 `/admin/` + `/api/admin/**`；仍需 JWT + 权限码（不变） |
| `/uploads/**` 商品图 | 可直接通过 `IP:8080` 取图 | 只经 nginx `/uploads/` 进入 |
| `/doc.html`、`/v3/api-docs/**`、`/webjars/**`、`/swagger-ui/**` | prod 已关闭（`api-docs.enabled=false`） | 边缘再统一 404，双保险 |
| `/actuator`、`/error`、`/druid`、`.git`、`*.sql/.bak/.log/.yml` | 未显式处理 | 边缘正则 location 统一 404 |
| MySQL `3306` | 未在应用内约束 | 不属于本仓库改动；部署时只监听 `127.0.0.1`，不随反代暴露（见「后续建议」） |
| 客户端里的后端地址 | 「我的」页可改地址；内网 IP 随包发出 | 生产构建锁定入口、下线调试卡片、内网 IP 不进产物 |

## 三、三层措施

### 1. 网络层：后端只监听回环

`HiddenWhite-backend/src/main/resources/application-prod.yml`

```yaml
server:
  address: ${SERVER_ADDRESS:127.0.0.1}   # 外部网络连不到 8080
  forward-headers-strategy: framework    # 反代带上 X-Forwarded-For 后才拿得到真实客户端 IP
  error:
    include-stacktrace: never
    include-message: never
    include-exception: false
```

- 反代与后端不同机（容器/另一台机器）时，把 `SERVER_ADDRESS` 改成**只对反代可达的内网地址**（如 `172.17.0.1`）。
- `application.yml`（base）**不设** `address`：本地开发仍监听全网卡，微信开发者工具与手机才能连 `http://本机IP:8080`。这是 dev 与 prod 的显式分界。

### 2. 边缘层：单入口 + 路径收敛

`deploy/nginx/hiddenwhite.conf`（新增）

- `/`、`/admin/` 静态站点；`/api/`、`/uploads/` 反代到 `upstream hiddenwhite_backend`（`127.0.0.1:8080`）。
- 每个反代 location 注入 `X-HW-Gateway $hw_gateway_secret`，密钥来自 `/etc/nginx/hw-gateway.conf`（`chmod 600`，不入库；示例见 `deploy/nginx/hw-gateway.conf.example`）。
- 限流：`hw_api` 300 r/min（burst 60）、`hw_auth` 30 r/min（burst 5，只作用于 `/api/auth/login|register`、`/api/admin/auth/login|captcha`），超限 429。
- 默认拒绝：`/actuator`、`/error`、`/doc.html`、`/swagger-ui*`、`/webjars`、`/v3`、`/druid`、隐藏文件、`*.sql|bak|log|conf|yml|yaml|properties` 一律 404。
- 安全头：HSTS、`X-Content-Type-Options`、`X-Frame-Options`（管理端 `DENY`）、`Referrer-Policy`；`server_tokens off`。
- `client_max_body_size 16m` 与后端 `spring.servlet.multipart.max-request-size` 对齐。

### 3. 应用层：网关密钥守卫

`HiddenWhite-backend/src/main/java/com/hiddenwhite/framework/filter/IngressGuardFilter.java`（新增）

- 校验请求头 `X-HW-Gateway` 与 `hiddenwhite.gateway.secret`（环境变量 `HW_GATEWAY_SECRET`）是否一致；不一致返回 `403` + 与 `R` 同构的 JSON。
- 比较走 `MessageDigest.isEqual`（定长、不提前返回），不做字符串逐字符比较。
- **不配置密钥时不启用**：本地开发零改动。
- 放行 `OPTIONS`（CORS 预检不承载数据，拦掉只会让跨域整体失败）。
- `@Order(HIGHEST_PRECEDENCE + 5)`：晚于 `TraceIdFilter`（403 响应带 traceId）、早于 `RateLimitFilter`（非网关流量不占限流配额）。
- 已有的 JWT（`JwtAuthenticationFilter`）、权限码（`@RequiresPermission`）、兜底 `denyAll()`、CORS 白名单（`hiddenwhite.cors.allowed-origins`）全部保留，本层只解决「谁能连到后端」。

### 4. 客户端层：入口收敛

| 位置 | 改动 |
|---|---|
| `HiddenWhite-front/config/backend.js` | 新增 `ENDPOINT_LOCKED`（生产构建 = 锁定）。锁定后：只用 `VITE_API_BASE_URL`，否则同源 `/api`；忽略并清除本地存储里的自定义地址；`setApiBaseUrl()` 变成空操作 |
| `HiddenWhite-front/config/backend-hosts.js` | 标注为「仅开发构建生效」，不再用于生产 |
| `HiddenWhite-front/vite.config.js` | 新增 `hw-strip-dev-backend-hosts` 构建插件：build 阶段把候选地址模块替换为 `[]`，内网 IP 不进产物 |
| `HiddenWhite-front/components/tabs/ProfilePanel.vue` | 「后端服务」调试卡 `v-if="devToolsVisible"`，**默认不渲染（开发构建也一样）**，需 `VITE_SHOW_BACKEND_DEBUG=true` 启动才显示；未显示时连探活请求都不发 |
| `HiddenWhite-front/.env.production.example` | 新增：`VITE_API_BASE_URL` 说明（小程序必填公网域名；H5 留空走同源） |
| `HiddenWhite-admin/vite.config.ts`、`HiddenWhite-front/vite.config.js` | dev 代理支持 `HW_GATEWAY_SECRET`，本地即可复现「带密钥」拓扑 |

## 四、部署步骤

```bash
# 1) 生成网关密钥（只存在服务器上）
openssl rand -hex 32

# 2) 后端：/etc/systemd/system/hiddenwhite.service 的 Environment= 里加
SPRING_PROFILES_ACTIVE=prod
SERVER_ADDRESS=127.0.0.1
HW_GATEWAY_SECRET=<上一步的值>
DB_PASSWORD=<数据库口令>
JWT_SECRET=<随机 32+ 字节>
CORS_ALLOWED_ORIGINS=https://coffee.example.com   # 同源部署可留空

# 3) nginx：写入密钥文件并放配置
sudo install -m 600 -o root -g root hw-gateway.conf /etc/nginx/hw-gateway.conf
sudo cp deploy/nginx/hiddenwhite.conf /etc/nginx/conf.d/
sudo nginx -t && sudo systemctl reload nginx

# 4) 前端产物落到站点根（一个 root 服务两个前端，见 nginx 文件头部注释）
#    /var/www/hiddenwhite/          ← 点单端
#    /var/www/hiddenwhite/admin/    ← 管理端
cd HiddenWhite-front && VITE_API_BASE_URL=https://coffee.example.com/api npm run build:h5
cd HiddenWhite-admin && npm run build
sudo rsync -a --delete HiddenWhite-front/dist/build/h5/ /var/www/hiddenwhite/
sudo rsync -a --delete HiddenWhite-admin/dist/        /var/www/hiddenwhite/admin/
```

> H5 的 `VITE_API_BASE_URL` 留空即可（走同源 `/api`）；**微信小程序必须填公网域名**，
> 并在微信公众平台「开发设置 → 服务器域名」登记该 https 域名。

## 五、验证方式（已实测）

**后端（prod profile，端口 8091 对照 8080）**

| 操作 | 期望 | 实测 |
|---|---|---|
| `netstat -ano \| grep 8091` | 只监听 `127.0.0.1` | `TCP 127.0.0.1:8091 LISTENING` |
| `curl http://127.0.0.1:8091/api/health` | 403 | `{"code":403,"message":"请通过统一入口访问",...}` |
| `curl -H "X-HW-Gateway: wrong" …` | 403 | 403 |
| `curl -H "X-HW-Gateway: <正确值>" …` | 200 | `{"code":200,...,"data":{"status":"UP"}}` |
| `curl --noproxy '*' http://10.30.153.120:8091/api/health` | 连不上 | `HTTP=000`（连接被拒） |
| 对照：老配置 `http://10.30.153.120:8080/api/health` | 200（**问题证据**） | 200 |
| dev profile（不配密钥）从局域网访问 | 200 | 200，`0.0.0.0` 监听不变 |

**前端（`npm run build:h5` 产物）**

| 检查 | 期望 | 实测 |
|---|---|---|
| 产物内搜索 `192.168.*` / `10.30.*` | 无命中 | 无命中 |
| 打开产物，「我的」页 | 无「后端服务」卡片 | 无 |
| 产物发出的接口请求 | 全部同源 `/api/**` | `/api/products`、`/api/store`、`/api/recommendations` |
| 产物请求 8080 | 0 次 | 0 次 |

**单元测试**

```bash
cd HiddenWhite-backend && ./mvnw -o -Dtest='IngressGuardFilterTest,IngressExposureTest' test
cd HiddenWhite-front  && npm test          # 35 项全绿（本次未新增前端用例，靠产物检查覆盖）
```

- `IngressGuardFilterTest`：未配密钥放行 / 缺头 403 / 错值 403 / 正确 200 / 配置值两端空白容错 / OPTIONS 放行。
- `IngressExposureTest`：prod 必须绑回环且不得含 `0.0.0.0`、必须声明 `HW_GATEWAY_SECRET`、密钥不得硬编码、base 配置不得摊到全网卡。

## 六、受影响的现有调用与兼容性

| 场景 | 影响 | 说明 |
|---|---|---|
| 本地 `npm run dev:h5` / `dev:mp-weixin` | **无影响** | dev 构建不锁定入口，仍走 vite 代理或内网探测；后端 dev profile 不绑回环、不校验密钥 |
| 手机真机 + 微信开发者工具连 `http://本机IP:8080` | **无影响**（dev） | dev profile 仍监听全网卡 |
| H5 生产构建 | **行为变化** | 以前会去探测内网 IP（部署到公网后必然失败）；现在固定同源 `/api`，需由 nginx 反代 |
| 小程序生产构建 | **必须配置** | `VITE_API_BASE_URL` 必填（端上不支持相对路径），且需在微信公众平台登记该 https 域名；缺参数时 `console.error` 明确报出，不再静默连内网 |
| 「我的」页改后端地址 / 长按自动探测 | **默认不可见** | 调试卡默认不渲染（开发构建也一样），需 `VITE_SHOW_BACKEND_DEBUG=true` 启动才出现；生产构建即使注入也不显示，`setApiBaseUrl()` 变空操作，已存的旧地址会被清除 |
| 管理端 | 无代码改动 | 本来就使用相对 `/api/admin`，同域部署天然适配；dev 代理仅新增可选密钥头 |
| `/api/health` 探活 | 需带网关密钥 | 运维巡检从本机 `curl` 时加 `-H "X-HW-Gateway: …"`；或直接经 nginx 访问 `https://域名/api/health` |
| 微信支付回调 `notify-url` | 需指向公网域名 | 已在 `application.yml` 用 `WECHAT_PAY_NOTIFY_URL` 配置；后端不再对外时，微信服务器只能经 nginx 回调，该地址要改成 `https://coffee.example.com/api/pay/notify` |
| 后端限流取客户端 IP | 更准确 | 新增 `forward-headers-strategy: framework` 后，`RateLimitFilter` 拿到的才是真实客户端 IP（此前反代场景下全是 `127.0.0.1`） |

## 七、后续建议（未纳入本次改动）

1. **数据库**：`3306` 只监听 `127.0.0.1`，或仅放行后端所在主机的内网地址；不要把 MySQL 与后端一起放到同一张公网网卡上。
2. **上传目录**：反代与后端同机时，`/uploads/` 可改为直接 `alias` 到 `data/uploads`，少一层转发（配置里已给注释）。
3. **管理端更严的来源限制**：`/api/admin/**` 可加 `allow <公司出口 IP>; deny all;`，或接入统一身份（SSO）。
4. **密钥轮换**：`HW_GATEWAY_SECRET` 与 `JWT_SECRET` 分开轮换；轮换时先改 nginx 再重启后端（或反过来，留一次短暂 403 窗口）。
5. **纵深防御**：如需跨公网多活，可在 nginx 前加 WAF / 云负载均衡，并把 mTLS 用于反代到后端这一段。
