## 一、背景与现状

1. **积分只增不减**：唯一变动入口是 `ShopRepository.awardOrderPoints()`（支付成功事务内，1 元 = 1 积分，向下取整，成长值 = 积分 × 10）。没有签到、没有消耗出口，`members.points` 是裸整数字段。
2. **无流水可追溯**：积分变动无任何记录，对账、客诉追溯均不可行——这正是开发清单 **P0-2** 登记的缺口（`开发清单.md:220-225`）。
3. **前端占位已留好**：`MemberPanel.vue` 的「积分明细」「积分兑换」入口目前全部弹「该会员服务当前仅展示权益说明，积分兑换与优惠券核销尚未开放。」，本方案即补齐这两个出口。
4. **`member_benefits` 不是商品**：它是会员卡背面的**规则说明文案表**（见 `PROJECT_MAP.md:17` 术语定义），不可复用为兑换品目录。
5. **金额抵扣先例**：`orders.discount` 列与报价接口 `/api/cart/quote`（返回 `subtotal/discount/packagingFee/total/count`）是现成的抵扣挂载点；目前唯一来源是首单立减 6 元（`OrderService.FIRST_ORDER_DISCOUNT`）。
6. **`products` 不适合兑换品**：其模型绑定奶咖假设（`has_milk`、SIZE/MILK/TEMPERATURE 规格单一分类 INT），无法表达 0 元/纯积分价/非饮品的兑换品，需新建表。
7. **管理员可直接改积分**：管理端 `Members.vue` 编辑五个字段（含 points），后端 `CoffeeService.updateMember` 仅校验非负——接流水后此路径必须同样留痕。

**术语约定**：本文「兑换品」指积分商城中可用积分兑换的商品（饮品券/周边）；「权益（benefit）」仍专指 `member_benefits` 文案表，二者不混用。

## 二、目标与范围

### 2.1 目标

- 会员可用积分**兑换兑换品**（到店核销），形成积分消耗闭环；
- **每一笔积分变动（发放/兑换/抵现/退回/管理员调整）均有流水**，从流水可反推任意时刻余额；
- 管理端可运营兑换品目录、核销兑换、查看兑换记录。

### 2.2 非目标（本期不做）

- 快递物流与收货地址（所有兑换品均到店核销/自提）；
- 优惠券实体化（`members.coupons` 仍是数量计数，实体券另立方案）；
- 真实微信支付改造（积分抵现的 0 元单边界已在规则中规避，见 3.3）；
- 积分过期清零（当前无过期策略，是否引入另行决策）。

### 2.3 分期

| 阶段 | 内容 | 估时 | 备注 |
|------|------|------|------|
| **A 积分流水** | 流水表 + 统一积分写入口 + 点单端「积分明细」页 | 0.5 天 | 即 P0-2 落地，兑换的前置 |
| **B 积分兑换** | 兑换品/兑换单表 + 点单端兑换页 + 管理端兑换品管理与核销 | 2 天 | 本方案核心 |
| **C 积分抵现** | 结算接入积分抵扣 | 0.8 天 | 增强项，可独立排期 |
| **D 增强**（按需） | 兑换统计看板、二维码核销、优惠券实体化、兑换品详情富文本 | 按需 | — |

## 三、业务规则

### 3.1 积分获取（维持现状，仅收紧写入口）

- 维持「支付成功发放，1 元 = 1 积分向下取整；金额 0 不发放」；
- **发放逻辑改为经统一流水入口记账**（见 5.1），杜绝双写路径；
- 抵现订单按**抵扣后实付金额**计积分——`awardOrderPoints` 本就取订单 `total`（已含立减/抵现），规则自动成立，需以单测固化，防「抵现又按原价拿分」套利。

### 3.2 积分消耗·兑换（阶段 B）

| 规则 | 设计 |
|------|------|
| 兑换定价 | 每个兑换品一个 `points_cost`；定价基准建议 **100 积分 ≈ 3 元等值**（即约 3% 消费返利），运营可调 |
| 限兑次数 | `per_member_limit`：0 = 不限；>0 时该会员「待核销 + 已核销」合计不得超限 |
| 库存 | `stock`：NULL = 不限；非空时原子递减，减至 0 即不可兑 |
| 核销码 | 8 位随机数字，全局唯一索引，生成冲突重试 |
| 有效期 | 兑换后 **30 天**内到店核销（`expires_at`），逾期未核销**自动退回积分**（惰性结算，见 5.4） |
| 自助取消 | 未核销（PENDING）时会员可自行取消，积分全额退回 |
| 退款语义 | 兑换扣分、退分各记一条流水（`REDEEM` / `REDEEM_CANCEL` / `REDEEM_EXPIRE_REFUND`），余额闭环 |
| 登录要求 | 兑换需会员登录；guest 会员不可兑换（余额恒 0 且无归属意义），未登录引导登录 |

### 3.3 积分消耗·抵现（阶段 C）

| 规则 | 设计 |
|------|------|
| 兑换比 | **100 积分 = 1 元**，`pointsToUse` 为任意正整数，折算金额保留 2 位小数 |
| 使用门槛 | 单笔至少使用 100 积分 |
| 抵扣上限 | ≤ 应付基数（小计 − 立减 + 包装费）的 **50%**，即实付至少一半——规避 0 元单，与真实微信支付（金额须 > 0）天然兼容 |
| 扣分时机 | 订单创建事务内扣分（`POINTS_DEDUCT`，`ref_order_id` = 订单 id）；订单取消（超时/手动/支付失败）按原因**全额退分**（`POINTS_REFUND`） |
| 与立减关系 | 叠加使用：先首单立减，后积分抵现，均计入 `orders.discount` |

### 3.4 管理员调整

`CoffeeService.updateMember` 保留「直接编辑积分」的 UI 不变，后端将**新旧差值**经统一流水入口落账（`ADMIN_ADJUST`，备注取表单内 displayName 变更说明或固定文案「管理端调整」）。后续可在会员详情加「积分明细」抽屉（复用 5.2 的流水查询）。

### 3.5 并发与一致性

- **扣分**：`UPDATE members SET points = points - ? WHERE id = ? AND points >= ?`，影响行数为 0 即「积分不足」（409），天然防超扣；
- **兑换事务**：扣分 →（同事务）限兑校验 → 库存递减 → 建兑换单 → 写流水，任一步失败整体回滚；同一会员的并发兑换因首先锁住 `members` 行而串行化；
- **流水 `balance_after`**：扣/加后同事务回读余额写入，任何一笔流水都能反推当时余额；
- **幂等**：过期退分、取消退分均以「条件状态翻转」（`WHERE status='PENDING' AND ...`）保证只发生一次。

## 四、数据模型（写入 `database/init.sql`）

风格对齐现有业务表（`created_at/updated_at`、ENUM 状态、注释清晰、`CREATE TABLE IF NOT EXISTS`；种子 `INSERT IGNORE`/`ON DUPLICATE KEY UPDATE`；存量库加列按 `information_schema` 判存 + `PREPARE/EXECUTE`）。

```sql
-- 1) 积分流水表（P0-2）
CREATE TABLE IF NOT EXISTS member_points_log (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    member_id VARCHAR(64) NOT NULL COMMENT '会员 id',
    change_amount INT NOT NULL COMMENT '变动量：正为发放/退回，负为消耗',
    balance_after INT NOT NULL COMMENT '变动后余额（同事务回读）',
    biz_type VARCHAR(32) NOT NULL COMMENT 'ORDER_AWARD / REDEEM / REDEEM_CANCEL / REDEEM_EXPIRE_REFUND / POINTS_DEDUCT / POINTS_REFUND / ADMIN_ADJUST',
    ref_type VARCHAR(32) NOT NULL DEFAULT '' COMMENT '关联对象类型：ORDER / REDEMPTION / ADMIN',
    ref_id VARCHAR(64) NOT NULL DEFAULT '' COMMENT '关联对象 id（订单/兑换单/管理操作）',
    remark VARCHAR(200) NOT NULL DEFAULT '',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    KEY idx_points_log_member (member_id, id),
    KEY idx_points_log_ref (ref_type, ref_id)
) ENGINE=InnoDB;

-- 2) 兑换品目录（独立于 products，不走奶咖规格模型）
CREATE TABLE IF NOT EXISTS redeem_products (
    id VARCHAR(40) NOT NULL COMMENT '业务主键，如 rw-americano',
    name VARCHAR(80) NOT NULL,
    subtitle VARCHAR(120) NOT NULL DEFAULT '',
    description VARCHAR(300) NOT NULL DEFAULT '',
    image VARCHAR(200) NOT NULL DEFAULT '' COMMENT '复用 /uploads 图片链路',
    points_cost INT NOT NULL COMMENT '兑换所需积分',
    stock INT NULL DEFAULT NULL COMMENT '库存：NULL 不限，非空须 >0 可兑',
    per_member_limit INT NOT NULL DEFAULT 0 COMMENT '每人限兑次数，0 不限',
    sort_order INT NOT NULL DEFAULT 0,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
) ENGINE=InnoDB;

-- 3) 兑换单（核销凭证）
CREATE TABLE IF NOT EXISTS redemptions (
    id CHAR(36) NOT NULL,
    redeem_no VARCHAR(32) NOT NULL COMMENT 'RW+yyyyMMdd+4 位日序号',
    member_id VARCHAR(64) NOT NULL,
    product_id VARCHAR(40) NOT NULL,
    product_name VARCHAR(80) NOT NULL COMMENT '快照',
    product_image VARCHAR(200) NOT NULL DEFAULT '' COMMENT '快照',
    points_cost INT NOT NULL COMMENT '快照：实际扣除积分',
    code VARCHAR(8) NOT NULL COMMENT '8 位核销码',
    status ENUM('PENDING','REDEEMED','CANCELLED','EXPIRED') NOT NULL DEFAULT 'PENDING',
    expires_at DATETIME(6) NOT NULL COMMENT '核销截止时间',
    verified_at DATETIME(6) NULL COMMENT '核销时间',
    verified_by VARCHAR(64) NULL COMMENT '核销管理员（sys_user.id）',
    cancelled_at DATETIME(6) NULL,
    created_at DATETIME(6) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_redemptions_no (redeem_no),
    UNIQUE KEY uk_redemptions_code (code),
    KEY idx_redemptions_member (member_id, created_at),
    KEY idx_redemptions_status_expire (status, expires_at),
    KEY idx_redemptions_product_limit (member_id, product_id, status),
    CONSTRAINT fk_redemptions_member FOREIGN KEY (member_id) REFERENCES members(id),
    CONSTRAINT fk_redemptions_product FOREIGN KEY (product_id) REFERENCES redeem_products(id)
) ENGINE=InnoDB;
```

## 五、后端设计

### 5.1 统一积分写入口（全应用唯一写路径）

新建 `com.hiddenwhite.common.points.PointsLedger`（JdbcTemplate 实现，放 `common/` 以便 shop 与 admin 两侧共用；若嫌包语义不符可下沉 `framework/`）：

```java
// 事务内执行：先动余额（条件更新防超扣），后记流水（balance_after 同事务回读）
// delta > 0 发放/退回；delta < 0 消耗，余额不足抛 BusinessException(409)
long adjust(String memberId, int delta, String bizType, String refType, String refId, String remark);
```

改造两个既有写点：

- `ShopRepository.awardOrderPoints()`：金额计算与成长值/晋升逻辑保留，积分部分委托 `PointsLedger.adjust(..., ORDER_AWARD, ORDER, orderId, ...)`（与 `transaction_id` 唯一防重的既有语义叠加，双保险）；
- `CoffeeService.updateMember()`：积分差值走 `ADMIN_ADJUST`（见 3.4）。

### 5.3 兑换事务流程（`RedeemService.exchange`）

```
@Transactional
1. 读兑换品并校验：enabled、积分足额（预检，最终以条件更新为准）
2. UPDATE members SET points = points - :cost WHERE id = :mid AND points >= :cost
   └ 影响行数 0 → 409「积分不足」；行锁同时把同会员并发兑换串行化
3. 限兑校验：SELECT COUNT(*) FROM redemptions
   WHERE member_id=:mid AND product_id=:pid AND status IN ('PENDING','REDEEMED')
   └ ≥ per_member_limit（>0 时）→ 409，事务回滚
4. UPDATE redeem_products SET stock = stock - 1
   WHERE id = :pid AND (stock IS NULL OR stock > 0)
   └ 影响行数 0 → 409「已兑完」，事务回滚
5. 生成兑换单：redeem_no（沿用 synchronized 取号模式）、8 位核销码（唯一冲突重试）、
   expires_at = now + 30 天、快照字段
6. 回读余额写流水：REDEEM，ref = REDEMPTION/:id
7. 返回兑换单（含核销码）
```

### 5.4 惰性过期结算（不引入定时任务基础设施）

`settleExpiredRedemptions()`：`SELECT ... WHERE status='PENDING' AND expires_at < NOW()` → 逐单条件翻转 `PENDING → EXPIRED`（`WHERE id=:id AND status='PENDING'` 保证幂等）→ 翻转成功者退分并记 `REDEEM_EXPIRE_REFUND` 流水。触发点：会员查「我的兑换单」、管理端查「兑换记录」、核销前校验。无需 scheduler。

## 九、风险与注意事项

1. **支付演示模式兼容**：阶段 B 不触碰支付链路；阶段 C 抵现以「实付 ≥ 50%」规则规避 0 元单，真实微信支付接入后规则无需变更；
2. **积分双写路径必须收口**：`awardOrderPoints` 与管理端改分若不同步接入 `PointsLedger`，流水立刻失真——实施时以全库检索 `points` 写点作为自检步骤；
3. **阶段 C 波及取消路径**：订单创建即扣分，`OrderService` 的超时/手动/支付失败取消均需挂退分钩子，与既有 `OrderCancelReason` 枚举对齐，逐路径补测；
4. **guest 会员**：兑换/明细接口拒绝 guest（401 → 引导登录），避免为无归属账号产生流水；
5. **文档同步**：`PROJECT_MAP.md:142` 对订单状态与支付字段的描述已滞后于代码，实施时按 CODESTYLE 第 6 节要求一并更正，并将本方案落地后的新表登记进 PROJECT_MAP 数据字典；
6. **主包体积**：两个新页面为纯列表/表单，无大图静态资源；兑换品图片走服务端 `/uploads` 外链，不进包。
