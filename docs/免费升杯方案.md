## 一、背景与现状

### 1.1 入口是假的

`MemberPanel.vue` 的「会员专属礼遇」是四张卡（`defaultBenefits`）：

```js
{ icon: 'gift',     title: '积分兑换', description: '好礼随心兑' },
{ icon: 'calendar', title: '生日礼遇', description: '生日专属惊喜' },
{ icon: 'percent',  title: '会员折扣', description: '指定商品专享' },
{ icon: 'cup',      title: '免费升杯', description: '每月专属礼遇' }
```

前三张都已经有承载物（兑换页 / 生日弹层 / 折扣详情页），**只有「免费升杯」点进去是 `showFeature()` 弹「正在筹备中」**。这张卡的文案与视觉已经定稿，缺的是它背后的一整套规则。

### 1.2 升杯在数据上是什么

杯型不是枚举，是 `product_options` 里 `option_type='SIZE'` 的行：

| label | extra_price | sort_order |
|---|---|---|
| 标准杯 240 毫升 | 0.00 | 1 |
| 大杯 360 毫升 | 6.00 | 2 |

下单时 `OrderService.buildItems` 把杯型差价直接加进单价：

```java
BigDecimal unitPrice = product.price().add(catalog.size(size).price());
```

**所以「升杯」= 把订单行的 `size_label` 换成高一档的杯型，并免掉这 6 元差价。**
不存在第三种解释——不是折扣、不是减免券、不是换购。

### 1.3 已有基础设施

| 设施 | 位置 | 本功能怎么用 |
|---|---|---|
| 积分账本 | `PointsLedger.adjust(delta, bizType, refType, refId)` | 扣/退升杯积分，条件扣减天然防超扣 |
| 等级阶梯 | `MemberLevels.levels()` | 策略表按等级建行，不重复定义等级 |
| 等级策略表范式 | `member_level_policies` | 策略表照此结构（`level_key` 主键 + 开关 + 文案） |
| 下单核销 / 取消退回 | `CouponService.markUsed` / `releaseForOrder` | 升杯记录完全同构：下单占用、取消释放 |
| 账单明细 | `order_discounts` + `DiscountLine` | 新增一个 `UP_SIZE` 类型，不动表结构 |

## 二、目标与范围

### 2.1 目标

- 「免费升杯」从静态文案变成**可判定、可核销、可追溯、可运营**的真实权益；
- 按会员等级区分升杯方式：**低等级用积分换，高等级直接免费**；
- 运营可在管理端按等级配置额度与积分价，不改代码；
- 每一次升杯都能在订单账单与积分流水里对上账。

### 2.2 非目标（本期不做）

- 跨品类升杯（如升燕麦奶、升超大杯）——杯型只有两档，模型按 `from_size/to_size` 留了扩展位；
- 升杯券（把升杯做成可转赠的券）——额度挂在会员身上，不可转让；
- 自动应用（结算时静默消耗额度）——见 5.2 的理由，必须显式勾选；
- 按门店/时段差异化额度。

### 2.3 分期

| 阶段 | 内容 | 验收 |
|---|---|---|
| **A 数据与策略** | 两张表 + 五档种子 + 策略读取 | 查库能看到 5 行策略 |
| **B 判定与额度** | `UpsizeService.decide()`：本月已用、免费/积分、额度耗尽 | 单测覆盖 5 档 × 3 种余额 |
| **C 下单接入** | 杯型替换 + 账单 `UP_SIZE` 明细 + 扣分 + 取消退回 | 真下单能升杯、能退分 |
| **D 点单端** | 礼遇卡四态 + 结算页开关 | 结算页勾选后杯型与金额同步变化 |
| **E 管理端** | 策略配置页 + 使用记录 | 改额度后点单端立刻生效 |

## 三、业务规则（核心）

### 3.1 等级规则矩阵

「每月」= **自然月**（Asia/Shanghai，1 号 00:00 重置），与优惠券的「自然周」同一套思路。

| 等级 | 成长值 | 每月免费次数 | 免费用完后 | 每月总次数 |
|---|---|---|---|---|
| 普通会员 | 0 | 0 | 200 积分 / 次 | 不限 |
| 白银会员 | 500 | 0 | 150 积分 / 次 | 4 |
| 黄金会员 | 1500 | **1** | 100 积分 / 次 | 6 |
| 铂金会员 | 4000 | **3** | 100 积分 / 次 | 8 |
| 钻石会员 | 10000 | **不限** | —（全免） | 不限 |

三条设计意图：

1. **金银之分就是「免费」与「付费」的分界**。黄金是第一次拿到「白送」的甜头（每月 1 次），
   这是升到黄金最直观的动机；
2. **积分价随等级递减**（200 → 150 → 100），低等级不是「不能升」，而是「升得更贵」——
   不留死路，只留价差；
3. **总次数上限只对中间三档设**。普通会员靠积分余额自我约束（200 分不是小数），
   钻石既然全免，再用次数卡它就失去了「身份感」的意义。

> 数值全部落在配置表里，上表是种子值，运营随时可改。

### 3.2 一次下单能用几次

**一次下单最多使用 1 次升杯额度，升级订单中的第一杯可升杯商品。**

理由：额度按「杯」计量，但一单多杯时要决定「哪几杯升」会引入新的选择界面与大量边界
（部分升级的账单怎么摊、取消时退几次）。第一版收敛为「一单一杯」，规则简单、账目清楚。
想升第二杯可以下次下单——`orders` 的「同时只能有一张进行中订单」确实挡不住这个诉求，
但这是已知取舍，写进 3.6 的边界表。

### 3.3 什么算「可升杯」

一行商品同时满足才可升：

1. 该行 `size` 等于策略的 `from_size`（默认「标准杯 240 毫升」）；
2. 该商品本身存在 `to_size` 这个杯型选项且 `enabled=1`；
3. 本单已经选中的行里，取**第一条**满足 1、2 的。

已经在 `to_size`（顾客自己点了大杯）的行**不参与**升杯——不能把「已经花 6 元买的大杯」
再算成一次免费升杯。

### 3.4 判定顺序（唯一真源）

```
used = 本月该会员 status='USED' 的记录数

if !策略存在 || !策略启用:           → 不可用（无资格）
if 本单没有可升杯的行:                → 不可用（本单已是最大杯型）

if freeQuota = -1（不限）:            → FREE
elif used < freeQuota:                → FREE
elif pointsCost > 0 且 (limit=-1 或 used < limit):
                                      → POINTS（需积分 ≥ pointsCost）
elif limit != -1 且 used >= limit:    → 不可用（本月次数已用完）
else:                                 → 不可用（该等级不支持积分升杯）
```

判定结果 `UpsizeDecision` 只有四种 `payType`：`FREE` / `POINTS` / `UNAVAILABLE` / `NOT_APPLICABLE`。

### 3.5 计价口径（最容易做错的地方）

**升杯不是「减 6 元」，而是「按大杯计价，再把 6 元作为优惠抵扣掉」。**

以「标准杯拿铁 30 元、黄金会员 8.5 折、满 30 减 5 券、用免费升杯」为例：

| 账单行 | 不用升杯 | 用升杯 |
|---|---|---|
| 商品金额 | 30.00 | **36.00**（大杯价，账面真实） |
| 会员折扣（8.5 折） | −4.50 | **−4.50** |
| 优惠券（满 30 减 5） | −5.00 | **−5.00** |
| 免费升杯 | — | **−6.00** |
| 合计 | 20.50 | **20.50** |

两个关键约束：

1. **折扣与券的基数必须是「原杯型金额」（30），不是账单商品金额（36）**。
   否则等于「白送 6 元的大杯，还要再打折、再用来凑券门槛」——送一次亏两次。
   实现上：`discountBase = subtotal − upsizeValue`。
2. **账单商品金额必须是 36**，因为 `order_items` 里存的是大杯，
   `Σ line_total` 必须等于 `subtotal`，否则管理端对账永远差 6 元。

### 3.6 边界与异常

| 场景 | 行为 | 理由 |
|---|---|---|
| 未登录 | 会员页不显示状态；结算页不出现该行 | 客户端无身份，无从判定 |
| 会员等级在阶梯外（如被手工改成「金卡会员」） | 查不到策略 → 不可用，**安静跳过**，不报错 | 与会员折扣一致：未知等级不打折，也不该阻断下单 |
| 策略 `enabled=0` | 不可用 | 运营关闭即全局下线 |
| 积分不足 | 报价返回 `POINTS` + `affordable=false`；下单抛 **409** | 见 3.7 |
| 本月次数用完 | 不可用，文案「本月已用完」 | — |
| 本单全是 `to_size` | 不可用，文案「本单已是最大杯型」 | 不能升「已经是大杯」的东西 |
| `from_size` 在 `product_options` 里被删/改名 | 找不到杯型 → 不可用；**并让测试失败** | 配置漂移要能被发现，而不是静默失效 |
| 顾客勾了升杯，但下单瞬间积分被别处扣光 | 抛 409，整单回滚，提示「积分不足，请取消升杯后重试」 | 不静默降级：付了钱却没升杯更难解释 |
| 下单成功后又取消（手动 / 超时） | 记录置 `RELEASED`，积分全额退回，额度恢复 | 「每月 N 次」实际是「每月成功使用 N 次」 |
| 取消后同月再下单 | 额度已恢复，可再次使用 | 刷单无利可图（退了分也退了额度，净收益 0） |
| 并发两次下单 | 单实例下被 `OrderService.create` 的 `synchronized` 串行化 | 与取号同源的技术债，见 8.3 |

### 3.7 积分不足时为什么报错而不是降级

用户勾选升杯 = 表达「我要这杯大杯」。此时如果静默按标准杯成交，他付了原价、拿到小杯，
**而且账单上看不出任何异常**，只能事后投诉。

报价阶段就把 `affordable` 告诉前端，勾选时就能拦住 99% 的情况；
下单时若仍失败（并发抢分），409 + 明确文案让顾客取消勾选重试，比「悄悄变成标准杯」诚实。

## 四、数据模型

### 4.1 `member_upsize_policies`（等级策略，每等级一行）

```sql
CREATE TABLE IF NOT EXISTS member_upsize_policies (
  level_key     varchar(30)  NOT NULL COMMENT '等级键，与 members.member_level 一致',
  level_name    varchar(30)  NOT NULL COMMENT '展示用等级名',
  monthly_limit int          NOT NULL DEFAULT 0  COMMENT '每月可用总次数；-1 = 不限',
  free_quota    int          NOT NULL DEFAULT 0  COMMENT '每月免费次数；-1 = 免费不限',
  points_cost   int          NOT NULL DEFAULT 0  COMMENT '免费额度用完后每次消耗积分；0 = 不再支持',
  from_size     varchar(40)  NOT NULL COMMENT '可升的起始杯型 label',
  to_size       varchar(40)  NOT NULL COMMENT '升级后的目标杯型 label',
  enabled       tinyint(1)   NOT NULL DEFAULT 1,
  note          varchar(120) NOT NULL DEFAULT '' COMMENT '点单端一句话说明',
  sort_order    int          NOT NULL DEFAULT 0,
  updated_at    timestamp    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (level_key)
) COMMENT='会员等级升杯策略（每等级一行）';
```

`-1 = 不限` 是唯一需要记住的魔法值。不用 `999` 是因为「999 次」和「不限」在语义上不同，
用正数表达无限早晚会有人按 999 去算余量。

### 4.2 `member_upsize_records`（使用记录，同时是额度计数依据）

```sql
CREATE TABLE IF NOT EXISTS member_upsize_records (
  id          bigint       NOT NULL AUTO_INCREMENT,
  member_id   varchar(36)  NOT NULL,
  level_key   varchar(30)  NOT NULL COMMENT '使用时的等级快照，客诉用',
  month_key   char(7)      NOT NULL COMMENT '归属自然月 yyyy-MM（Asia/Shanghai）',
  pay_type    varchar(10)  NOT NULL COMMENT 'FREE / POINTS',
  points_cost int          NOT NULL DEFAULT 0 COMMENT '实扣积分',
  size_from   varchar(40)  NOT NULL,
  size_to     varchar(40)  NOT NULL,
  order_id    char(36)     NOT NULL COMMENT '核销到哪笔订单',
  status      varchar(12)  NOT NULL DEFAULT 'USED' COMMENT 'USED / RELEASED',
  created_at  datetime(6)  NOT NULL,
  released_at datetime(6)  DEFAULT NULL,
  remark      varchar(120) NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  KEY idx_upsize_member_month (member_id, month_key, status),
  KEY idx_upsize_order (order_id)
) COMMENT='会员升杯使用记录（下单占用、取消释放）';
```

**为什么用 `month_key` 冗余列**：额度统计是「按月分组」而不是「按时间范围扫」。
`DATE_FORMAT(created_at,'%Y-%m')` 会让索引失效（项目既有约定：不对列套函数），
`WHERE created_at >= ? AND created_at < ?` 又要在 Java 里算月初月末。
存一个 `char(7)` 既省事又走得上 `(member_id, month_key, status)` 索引。

**为什么不给 `(member_id, month_key)` 建唯一索引**：一个月合法使用多次，
唯一约束在这里既拦不住超用（次数是变量），又会误拦正常记录。额度并发见 8.3。

## 五、状态流转

### 5.1 记录状态机

```
       下单（勾选升杯 + 额度判定通过）
                  │
                  ▼
              ┌───────┐
              │ USED  │──── 订单取消（手动 / 超时） ──▶ RELEASED
              └───────┘         （退积分 + 恢复额度）
                  │
                  └── 订单完成取餐 ──▶ 保持 USED（额度已真实消费）
```

`RELEASED` 是**终态**，不再回到 `USED`——顾客要再升杯就重新下单，产生新记录。
这样每一次「额度被占用」都有独立行，`SELECT COUNT(*) WHERE status='USED'` 就是当月真实占用数。

### 5.2 订单生命周期中的挂载点

| 时机 | 动作 | 事务 |
|---|---|---|
| 报价 `quote()` | 只判定，**不写记录、不扣分** | 无 |
| 下单 `create()` | 判定 → 改杯型 → 写记录(USED) → 扣分 → 写 `order_discounts` | 与订单同一事务 |
| 取消 `cancel()` | 记录→RELEASED → 退分 | 与订单取消同一事务 |
| 超时 `OrderTimeoutJob` | 同上 | 同上 |
| 完成 `complete()` | 无动作 | — |

**必须与订单同事务**：任何一步失败都要整体回滚，绝不允许出现
「升了杯没扣分」或「扣了分没升杯」的中间态。`PointsLedger` 本身是 `REQUIRED` 传播，
会自然加入外层事务。

### 5.3 为什么不在报价时预占额度

报价页可以反复刷新、来回切券，每次都预占会让额度凭空减少。
与优惠券的「报价不核销、只有落单才扣」保持同一条原则。

## 六、接口设计

### 6.1 点单端

**`GET /api/upsize/status`**（需登录）——会员页卡片与结算页的唯一状态源

```json
{
  "available": true,
  "levelKey": "黄金会员",
  "levelName": "黄金会员",
  "freeQuota": 1,
  "freeUsed": 0,
  "freeLeft": 1,
  "monthlyLimit": 6,
  "usedThisMonth": 0,
  "pointsCost": 100,
  "fromSize": "标准杯 240 毫升",
  "toSize": "大杯 360 毫升",
  "sizeDiff": 6.00,
  "pointsBalance": 320,
  "affordable": true,
  "reason": "",
  "note": "每月 1 次免费，之后 100 积分"
}
```

`reason` 只有不可用时才有值，取值固定为：
`NO_POLICY` / `DISABLED` / `LIMIT_REACHED` / `NO_POINTS_COST` / `SIZE_MISSING`，
前端据此决定文案，不靠字符串猜。

**报价 `POST /api/cart/quote`** 请求体新增 `useUpsize: boolean`

响应 `PriceSummary` 新增一段：

```json
"upsize": {
  "applied": true,
  "payType": "FREE",
  "pointsCost": 0,
  "sizeFrom": "标准杯 240 毫升",
  "sizeTo": "大杯 360 毫升",
  "sizeDiff": 6.00,
  "itemIndex": 0
}
```

**下单 `POST /api/orders`** 请求体同样新增 `useUpsize`。

## 七、点单端交互

### 7.1 会员礼遇卡（四态，与生日卡同构）

| 状态 | 第二行文案 | 角标 |
|---|---|---|
| 有免费额度 | `本月还可免费升 2 次` | 可领取（金色描边） |
| 免费已用完，可积分 | `100 积分 / 次` | — |
| 本月次数用完 | `本月已用完` | — |
| 无资格 / 关闭 | `暂不可用` | — |

点击行为：不再弹「筹备中」，改为进入**升杯说明页**（弹层即可，内容少），
展示「本月额度 + 本等级规则 + 全部等级对比」，底部一个「去点单」按钮。
不做独立页面——权益说明内容量撑不起一个页面，参考折扣详情页的「一屏滚动」反而更重。

### 7.2 结算页（关键交互）

账单区新增一行，位于「优惠券」之后：

```
免费升杯     标准杯 → 大杯 · 本月免费剩 1 次      [开关]
```

- 可点击时右侧是一个滑动开关（复用 `SlideConfirm` 之外的轻量 toggle），
  或直接整行点击切换（与「优惠券」整行点击一致，成本更低）；
- 切换后立刻重算：商品金额 +6，新增「免费升杯 −6」行，商品行杯型变「大杯」；
- 不可用时整行置灰，右侧显示原因（「本单已是最大杯型」/「本月已用完」/「积分不足」）。

**为什么必须显式勾选而不是自动应用**：免费额度是稀缺资源（黄金每月 1 次），
自动消耗会让顾客在「其实不需要大杯」的那一单里被悄悄扣掉，
而且他事后在会员页看到「本月已用完」会完全想不起来什么时候用的。

### 7.3 视觉

- 图标：沿用 `icon-set.json` 里已登记的 `cup`（图片中的金线杯子），不新增图标；
- 卡片配色、圆角、动效全部走 `tokens.scss`，不新增色值；
- 结算页那一行的样式复用 `.bill-row--action`（优惠券行同款）。

### 8.2 `calculate` 的改造（最容易回归的地方）

现状签名：

```java
private PriceSummary calculate(BigDecimal subtotal, List<OrderItem> items, String owner,
                               Coupon coupon, AppliedDiscount levelDiscount)
```

改为：

```java
private PriceSummary calculate(BigDecimal subtotal, BigDecimal upsizeValue, List<OrderItem> items,
                               String owner, Coupon coupon, AppliedDiscount levelDiscount)
```

内部只改一处：所有「折扣基数」从 `subtotal` 换成 `discountBase = subtotal.subtract(upsizeValue)`，
而账单金额、`total` 仍以 `subtotal` 为准。券门槛同理用 `discountBase`。

**必须补的单测**（现有 `OrderServiceTest` 已覆盖大量组合，新用例沿用它的事务/仓储 mock 风格）：

1. 免费升杯 + 会员折扣 + 券：`total` 与不用升杯时完全相等；
2. 升杯单价不计入券门槛（原价 29 + 升杯 6 = 35，满 30 的券**不应**生效）；
3. 升杯部分不被会员折扣打折（折扣金额等于按原杯型算的结果）；
4. `Σ order_items.line_total == subtotal`（对账闭合）；
5. 积分升杯：扣分成功、余额不足抛 409 且订单未落库；
6. 取消订单：积分退回、记录 `RELEASED`、当月额度恢复。

### 8.3 并发风险（已知并接受）

额度判定是「先 `COUNT` 再 `INSERT`」，两次并发下单理论上都能看到「还剩 1 次」。

- **当前**：`OrderService.create` 带 `synchronized`（单实例），下单本身已串行，风险为 0；
- **多实例**：该锁不跨进程，会超用 1 次。彻底方案是「额度行 + `SELECT ... FOR UPDATE`」
  或按 `(member_id, month_key, seq)` 建唯一索引让第二次插入失败。
  这与「取餐号先查后写」是同一笔技术债，不在本功能单独解决，但必须在代码注释里写明。

### 8.4 配置漂移的护栏

`from_size` / `to_size` 存的是 label 字符串，杯型改名就会失效。补一条测试：
读 `init.sql` 的种子与 `product_options` 的杯型 label 比对，任一侧改动而另一侧没跟，
测试直接失败（与 `ImageProcessorTest` 读 yml 断言尺寸是同一手法）。

## 十、与既有优惠的关系（一句话总结）

> **升杯是「实物升级」，不是「价格优惠」**：它先把商品金额抬高 6 元，再把这 6 元抵掉。
> 它对会员折扣与优惠券完全中立——不参与打折、不参与凑门槛，
> 顾客实付金额与不用升杯时一模一样，只是拿到的是大杯。

这条是整套设计的锚点。任何实现如果让「用升杯」和「不用升杯」的实付金额出现差异，
就是做错了。
