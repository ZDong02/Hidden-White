# 每周优惠券功能设计方案

| 项 | 内容 |
|----|------|
| 状态 | 已实施（V1，2026-11-04） |
| 日期 | 2026-11-04 |

## 一、需求与关键决策

> 原始需求：每周每名用户可领取一张满减 6 元的优惠券。

需求只给了一句话，其余全是必须由实现方拍板的规则。下面每条都给了「为什么这样定」，
因为这些取舍直接影响顾客会不会觉得「被套路」，也直接影响门店会不会亏。

| 决策点 | 结论 | 理由（一句话） |
|--------|------|----------------|
| 领取周期 | **自然周**（周一 00:00 – 周日 24:00，Asia/Shanghai） | 「每周一重置」一句话说得清；滚动 7 天要顾客自己记上次领取时刻 |
| 重置方式 | 周一 00:00 归零，**额度不累积** | 累积会让长期不用的人一次领 4 张，与「每周一张」的初衷相反 |
| 每期限额 | **每人每周 1 张**（硬规则，不做配置） | 需求原话；可配置会让唯一索引与业务校验两处不一致 |
| 有效期 | **领取时刻 + 7 天**（精确到分钟，可配 1–90 天） | 按自然周末失效会惩罚周末领取的人（只剩 1 天） |
| 面额 | **6 元**（可配，上限 200 元） | 需求原话 |
| 使用门槛 | **订单商品金额 ≥ 20 元**（可配） | 无门槛的 6 元券 = 16 元咖啡卖 10 元，等于半价促销且不可控 |
| 适用范围 | **点单端到店自提订单**，按商品金额（不含包装费）判定 | 积分兑换单不走金额结算，券没有可抵扣的金额 |
| 叠加 | **单笔限 1 张，且与首单礼遇互斥，系统自动取优惠更大的一边** | 两者都是 6 元级见面礼，叠加会让一杯 22 元咖啡落到 10 元 |
| 持有上限 | 手上最多 **2 张**未使用（可配，0 = 不限） | 有效期 7 天 + 每周一张 ⇒ 正常使用最多重叠 2 张；上限是防囤积的兜底 |
| 发行量 | 可设总发行量，**留空 = 不限量** | 门店做「限量 200 张」活动时不必改代码 |
| 过期处理 | **惰性结算**，无定时任务 | 状态翻转晚几分钟没有业务影响，不值得引入调度基础设施 |

## 二、领取周期与重置规则

### 2.1 自然周的边界

```
周一 00:00:00  ────────────────  周日 23:59:59.999
        ↑ 本周开始                    ↑ 下周一 00:00 重置
```

- 时区固定 `Asia/Shanghai`（`Constants.ZONE`），**不取 JVM 默认时区**：服务器跑在 UTC 时，
  「今天周几」会整体偏移 8 小时，周日夜里的领取会算进下一周。
- 周起点是 **ISO-8601 的周一**（`DayOfWeek.MONDAY`），不是 `Calendar` 默认的周日。
  用周日当起点会让「周日领的」和「周一领的」落在同一周，顾客看到「本周已领」却毫无印象。
- **跨年不切分**：2027-01-01（周五）属于 2026-12-28 那一周。若按自然年切分，
  会员在跨年夜就能连领两次。

### 2.2 幂等键：本周周一的日期

`member_coupons.week_key` 存 `yyyy-MM-dd`（**本周周一**，如 `2026-11-02`），与 `member_id`
组成唯一索引 `uk_coupon_member_week`。

**为什么不用 ISO 周号（`2026-W45`）**：跨年时会出现 `2026-W53` 接 `2027-W01` 这种编号，
人对它的直觉几乎为零；`2026-12-28` 一眼能看出是哪一周，而且字符串排序即时间排序，
运营端按周筛选不必做任何换算。

`CouponWeek` 是这段逻辑的唯一实现（含 `resetAt()` 返回下周一 00:00），
前端不做任何日期比较。

### 2.3 重置后的额度

不累积。周日 23:59 没领，周一照样只有 1 张 —— 与「每周一张」的语义一致，
也避免「攒了 4 周一次领 4 张」把发行量瞬间打穿。

## 三、领取入口与触发方式

**唯一领取入口：券包页**（`pages/coupons/index`）。入口有三个，都指向同一页：

| 入口 | 位置 | 行为 |
|------|------|------|
| 会员面板「优惠券」格子 | 会员页数据概览第二个格子 | 点进券包；本周可领时数字旁显示金色「可领」小标 |
| 券包页顶部券面卡 | 券包页首屏 | 卡内主按钮「领取本周好券」 |
| 未登录时的任意入口 | 上述两处 | 先跳登录页，登录成功后按 `redirect=coupons` 直接落到券包 |

**触发方式只有一种：用户主动点击。** 不做「进页面自动发放」——
自动发放会让「我的券包为什么多了一张」变成无法解释的事，也让客诉无法定位。

领取成功后按钮立即变为「本周已领取」（禁用态），并在会员卡上刷新券数，
不需要顾客自己退出再进来确认。

## 四、券面规则

| 属性 | 值 | 判定位置 |
|------|-----|----------|
| 面额 | 配置值（默认 ¥6） | 领取时**快照**进券记录 |
| 门槛 | 配置值（默认 ¥20） | 领取时快照；按 `订单商品金额` 判定 |
| 有效期 | 领取时刻 + N 天（默认 7） | `expires_at` 精确到分钟 |
| 门槛基数 | `subtotal`（商品金额，**不含包装费**） | `OrderService.calculate` |
| 适用范围 | 点单端自提订单 | 其它链路不读取券 |

**为什么是快照**：运营把面额从 6 调到 8，已领的 6 元券仍是 6 元。
否则顾客截图里是 6 元、结算时扣 8 元（或反过来），都是对账事故。

**门槛为什么按商品金额、不含包装费**：包装费是履约成本，不是商品价值。
把它算进门槛，会让「差 1 元凑单」的顾客以为占了便宜，实际多付了包装费。

## 五、单笔订单的使用限制与叠加规则

1. **单笔订单最多使用 1 张券**。多张会让「省了多少」难以向顾客解释，也让退款分摊变复杂。
2 **与首单礼遇互斥，取优惠更大的一边**：
   ```
   discount = max( 首单礼遇金额 , 券面额 )      // 券面额受订单金额截断
   ```
3. **券没被采用时不核销**。新客手上同时有首单礼遇（6 元无门槛）与一张券（6 元满 20）时，
   两者金额相等 → 走首单礼遇，券原样保留到下一次。这是「不让顾客吃亏」的落点：
   无条件用券会让新客白丢一张本可以留到下次的券。
4. **券不能与积分抵现叠加**（当前无积分抵现链路，保留此约束以免将来误加）。
5. 券**只抵扣商品金额**，抵扣额不超过商品金额本身（`min(面额, subtotal)`），
   订单实付不会出现负数。

服务端在报价结果里回传 `discountLabel`（「首单礼遇」/「每周好券」）与 `couponId`
（仅真正采用时非空），前端据此显示「减的是哪一笔」，不需要自己反推。

## 六、领取状态校验（防重复领取）

### 6.1 校验顺序

```
① 功能是否开放（config.enabled）
② 配置是否可用（面额 > 0、有效期 > 0）
③ 结算过期券 → 本周是否已领（week_key 命中即「已领」，直接返回那张券）
④ 持有上限（未使用 + 未过期 ≥ maxHeld → 409）
⑤ INSERT（唯一索引兜底并发）
⑥ 扣库存（条件更新，0 行 → 409 并回滚⑤）
```

### 6.2 防重复的三道闸

| 闸 | 实现 | 拦住什么 |
|----|------|----------|
| 业务预检 | 按 `week_key` 查本周记录 | 连点、刷新后重点 —— 给出友好文案而不是报错 |
| **数据库唯一索引** | `uk_coupon_member_week(member_id, week_key)` | **并发双发**（两个请求同时通过预检） |
| 唯一键冲突回滚 | 捕获 `DuplicateKeyException` → 返回已有券 | 让第二个请求的体验等同「已领取」，不弹红色错误 |

**为什么绝不能「先查后写」**：两个并发请求会读到同样的「尚未领取」快照，双双插入 →
一个会员一周拿两张券，是实打实的资损。唯一索引是唯一可靠的互斥点。

### 6.3 重复领取的语义

已领取时 **返回 200 + 同一张券**，不抛错。理由：顾客连点两下、或领完滑回来再点，
期待的是「看到那张券」，而不是一句「你已领过」的红字。与生日礼遇的领取口径一致。

### 6.4 本周状态（服务端算好下发）

| `weekState` | 触发条件 | 券包按钮 |
|-------------|----------|----------|
| `CLAIMABLE` | 未领 + 有库存 + 未超持有上限 | 「领取本周好券」（可用） |
| `CLAIMED` | 本周已有记录 | 「本周已领取」（禁用） |
| `HOLD_LIMIT` | 未使用张数 ≥ 上限 | 状态文案「手上还有 N 张未用」（禁用） |
| `SOLD_OUT` | 发行量耗尽 | 「本周已领完」（禁用） |
| `DISABLED` | 配置关闭 | 「暂未开放」（禁用） |

优先级按上表自上而下：**已领取 > 售罄 > 持有超限 > 可领**。
已领取的人即使库存耗尽也该看到「已领取」，而不是「已领完」。

## 七、库存与并发处理

### 7.1 库存写在配置行上

```sql
UPDATE coupon_config SET issued_count = issued_count + 1
WHERE id = 1 AND (total_stock IS NULL OR issued_count < total_stock)
```

- **自增 + 条件**，不是「先读再写」：后者在并发下会丢更新，库存 100 张能发出去 120 张。
- 影响行数 0 ⇒ 已领完，抛 409 让事务回滚，刚插入的券记录一并消失。

### 7.2 写入顺序：先 INSERT 再扣库存

| 顺序 | 并发冲突时的代价 |
|------|------------------|
| **INSERT → 扣库存**（现行） | 第二个请求根本碰不到库存，无需补偿 |
| 扣库存 → INSERT | 必须在唯一键冲突时手工回补库存，回补语句一旦失败就永久少一张可发量 |

### 7.3 核销的互斥

```sql
UPDATE member_coupons SET status='USED', used_at=?, order_id=?, discount_amount=?
WHERE id=? AND member_id=? AND status='UNUSED' AND expires_at > ?
```

条件更新是唯一互斥点：重复提交 / 并发下单时第二次影响 0 行 → 409 → 下单事务回滚。
**不会出现「一张券挂在两笔订单上」。**

下单方法带 `@Transactional`，订单落库与券核销同一事务：核销失败连订单一起回滚，
不会出现「钱按优惠算了、券却没扣」的资损。

### 7.4 取消订单必须退券

下单即核销的模型下，不退券等于「点一下白丢 6 元」，且账面没有任何痕迹。

```sql
UPDATE member_coupons
SET status = CASE WHEN expires_at <= NOW() THEN 'EXPIRED' ELSE 'UNUSED' END,
    used_at = NULL, order_id = NULL, discount_amount = 0
WHERE order_id = ? AND status = 'USED'
```

- 用 `CASE` 在一条语句里重判有效期：券在订单上停留期间可能已过期，直接恢复成
  `UNUSED` 会让一张过期券复活。
- 幂等：条件 `status='USED' AND order_id=?`，重复调用第二次影响 0 行。
- 覆盖两条取消路径：顾客主动取消（`OrderService.cancel`）与超时任务
  （`OrderTimeoutJob.cancelOne`）。

### 7.5 惰性过期

```sql
UPDATE member_coupons SET status='EXPIRED'
WHERE member_id=? AND status='UNUSED' AND expires_at <= NOW()
```

在三个真正会读到状态的入口前触发：券包、结算页可用券、管理端记录（全量版）。
理由与 `RedeemService.settleExpired()` 一致 —— 日活几十人的点单端不值得为一次
状态翻转引入调度基础设施，而这三个入口覆盖了所有会看到券状态的场景。

## 八、记录保存

### 8.1 两张表

```
coupon_config    单行（id=1）  全局配置 + 发行量计数器
member_coupons   券本身        领取记录 = 使用记录（同一行）
```

`member_coupons` 一行同时回答三个问题：

| 问题 | 字段 |
|------|------|
| 谁在哪一周领的 | `member_id` + `week_key` + `claimed_at` |
| 这张券长什么样 | `title` / `amount` / `min_spend`（领取时快照） |
| 用在哪、什么时候用的、抵了多少 | `order_id` / `used_at` / `discount_amount` |
| 现在什么状态 | `status`（`UNUSED` / `USED` / `EXPIRED`）+ `expires_at` |

### 8.2 为什么不做独立的「使用记录表」

券只有三态且一次核销即是终态，使用信息就是券行的几个列。另建一张表意味着
「券」与「用券记录」要保证 1:0..1 的一致性，多一个可能对不上的地方。

### 8.3 `members.coupons` 的处置

`members.coupons` 是早期没有券表时留下的裸计数列，从未被任何业务流程维护过（恒为 0）。
现在**会员卡上的券数一律以券表为准**（`CouponService.unusedCount`：未使用且未过期），
由 `MemberService.get` 覆盖该字段，前端零改动。

不去删这一列：`Members.vue` 的编辑表单仍在写它，删列会连带改动管理端表单；
等表单改造时一并清理（见 §14）。

## 九、用户端展示与提示

### 9.1 券包页（`pages/coupons/index`）

| 区域 | 内容 |
|------|------|
| 首屏券面卡（深色） | 面额、门槛、有效期、状态角标、重置提示、领取按钮 |

| 即将过期 | 剩余 ≤ 1 天时显示「不足 1 天到期，尽快使用」 |
| 空态 | 「还没有优惠券，每周一记得来领一张」 |
| 脚注 | 「每周一 00:00 重置，每位会员每周可领一张；单笔订单限用一张，与首单礼遇不叠加。」 |

**状态 → 文案对照**（全部由服务端下发，前端只显示）：

| 场景 | 券面角标 | 按钮 |
|------|----------|------|
| 可领取 | 本周可领取（金底） | 领取本周好券 |
| 已领 | 本周已领取 | 本周已领取（禁用） |
| 售罄 | 本周好券已领完 | 本周好券已领完（禁用） |
| 持有超限 | 手上还有 N 张未用 | 同上（禁用） |
| 未开放 | 本周好券暂未开放 | 暂未开放（禁用） |

重置提示固定为「下周一 11月9日 00:00 后可再领」，**由服务端格式化**，
不让各机型各自解释日期。

### 9.2 结算页（`pages/checkout/checkout.vue`）

- 账单区「优惠」行显示 `discountLabel −¥N`；无优惠时显示「暂无可用优惠」。
- 点击打开选券弹层：可用券可点选，**不可用券也列出**（灰卡 + 「还差 ¥4 可用」）——
  券包里有、结算页消失，顾客会以为券丢了。
- 选中后立即重新报价；报价失败则回滚选择，避免「弹层显示已选、账单没减」。
- 选了券但首单更划算时，弹层底部提示「本单首单礼遇更划算，这张券已为你保留」。

### 9.3 会员面板

- 「优惠券」格子显示未使用张数，本周可领时在数字旁加金色「可领」小标。
- 领券成功回来后自动重拉会员资料，券数立即变化。

## 十、后台配置与管理功能点

### 10.1 页面：咖啡运营 → 优惠券（菜单 409，`coffee/coupon/index`）

**左栏：券配置**

| 字段 | 说明 | 服务端校验 |
|------|------|-----------|
| 是否开放 | 点单端能否领取 | — |
| 券面额 | 元 | > 0 且 ≤ 200 |
| 使用门槛 | 元，0 = 无门槛 | ≥ 0 且（> 0 时）≥ 面额 |
| 有效期 | 天 | 1–90 |
| 持有上限 | 张，0 = 不限 | 0–10 |
| 总发行量 | 留空 = 不限量 | ≥ 0 且 ≥ 已发出数 |
| 券标题 / 副标题 / 使用说明 | 点单端文案 | 必填 / 长度上限 |

「门槛 ≥ 面额」这条校验的必要性：门槛低于面额意味着减完之后订单可能为负，
虽然不会真的扣负数，但券的价值完全失真。

「发行量 ≥ 已发出数」：否则页面会出现「剩余 −12 张」，且已发的券无法回滚。

**左栏还有**：本周概览（本周已领 / 本周核销 / 当前未使用 / 累计抵扣）+
**1:1 券面预览**（尺寸 = rpx ÷ 2，与点单端券包首屏同一套视觉）。改面额时即时可见，
避免运营「凭想象调数字」。

**右侧：发放与使用记录**

列：会员（昵称 + ID 前缀）、手机号、归属周、面额、状态、领取时间、使用时间、
核销订单号、抵扣金额。

筛选：状态（待使用/已使用/已过期）、归属周（最近 12 周）、关键词（昵称/手机号/会员 ID）。

查询前先跑一次全量过期结算：不结算的话，运营会把早作废的券统计成「待使用」，
按这个数字答复顾客一定是错的。

### 10.2 权限

| 权限码 | 用途 |
|--------|------|
| `coffee:coupon:list` | 查看页面与配置 |
| `coffee:coupon:edit` | 保存配置（记操作日志） |
| `coffee:coupon:records` | 查看发放记录 |

配置写入走 `@OperLog`：改一个数字就影响全体会员接下来能省多少钱，必须留痕。

## 十一、边界情况与用户可见反馈

| 场景 | HTTP | 服务端文案 | 用户看到 |
|------|------|-----------|----------|
| 重复领取 | 200 | —（返回同一张券） | 正常提示「已放入券包，X 前有效」，无红字 |
| 本周券已领完 | 409 | 本周好券已被领完，下周一再来看看 | 红色提示，按钮变「本周好券已领完」 |
| 持有超限 | 409 | 您手上还有 N 张券未使用，先用掉一张再来领 | 红色提示，角标「手上还有 N 张未用」 |
| 功能关闭 | 409 | 每周好券暂未开放，下次再来看看 | 红色提示，券面角标「暂未开放」 |
| 配置不完整 | 409 | 优惠券配置不完整，请联系门店 | 红色提示（运营侧配置事故） |
| **已使用** | 409 | 该优惠券已使用（订单 2c70c396），请选择其它优惠券 | 弹层里该券不可选；结算时切回不用券 |
| **已过期** | 409 | 该优惠券已于 2026-11-03 23:16 过期 | 券列表标「已过期」，结算页不可选 |
| 门槛不足 | 409 | 该券满 ¥20 可用，当前商品金额 ¥16 | 灰卡 + 「还差 ¥4 可用」 |
| 券不属于本人 / 不存在 | 404 | 优惠券不存在或已失效 | 提示后自动切回「不使用优惠券」 |
| 券在结算期间失效 | — | 前端捕获后清空选择并重新报价 | 「所选优惠券已失效，已为你取消使用」 |
| 未登录 / 游客账号 | 401 | 请先登录 / 游客账号无法使用优惠券 | 跳登录页，成功后回券包 |

**错误码约定**：券相关的失败全部是 409（状态不允许）或 404（不存在），
`CouponException` 自带 `HttpStatus`，由 `GlobalExceptionHandler` 按路径转成
点单端的 `ApiError` 或管理端的 `R` —— 与 `PointsException` / `BirthdayException` 同一套路。

**前端不能自己编文案**：所有 409 的原因都是「一句话说清 + 给出下一步」的完整句子，
前端直接透出 `error.message`，不做二次包装 —— 二次包装会把「什么时候再来」这类
关键信息丢掉。

**单测**

- `CouponWeekTest`：周一/周日同周、跨周、重置时刻、跨年不切分、键可排序；
- `OrderServiceTest`：券与首单礼遇取优（相等 / 券更大 / 老客）、券未采用不核销、
  取消订单退券。

**契约测试**：`admin/src/api/__tests__/coupon.test.ts` 锁 URL 与请求体形状
（含 `totalStock: null` 必须原样出现在 body 里 —— 被丢掉就变成另一种业务语义）。

**真接口验证（2026-11-04，8081 端口 + 本地库）**

| 用例 | 结果 |
|------|------|
| 领券 → 券包 CLAIMED、到期 = 领取 + 7 天、重置提示「下周一 11月9日 00:00」 | ✅ |
| 重复领取 | 200，券数仍为 1 |
| 32 元可用 / 16 元不可用 | 「还差 ¥4 可用」 |
| 新客带券报价 | 走首单礼遇，`couponId=null`，下单后券仍 `UNUSED` |
| 老客带券报价 | 走券，`discountLabel=每周好券`，下单后券 `USED` 且带 `orderId`、抵扣 6 |
| 已用券复用 | 409「该优惠券已使用（订单 xxx）」 |
| 取消订单 | 券退回 `UNUSED`，会员卡券数同步为 1 |
| 券过期（改库造数据） | 券包 `EXPIRED`、报价 409、可用券 0 |
| 发行量 = 已发 | 领取 409「本周好券已被领完」，券包 `SOLD_OUT` |
| 持有 2 张 | `HOLD_LIMIT`，领取 409「您手上还有 2 张券未使用」 |
| 未登录访问券包 | 401 |
| 管理端配置读取/保存/非法门槛拒绝/记录分页/周下拉 | 全部通过 |

**执行 `init.sql` 的坑**：Windows 下 mysql 客户端默认字符集不是 utf8mb4，
带中文 `DEFAULT` 的建表语句会报 `ERROR 1067 Invalid default value for 'subtitle'`。
必须加 `--default-character-set=utf8mb4`。

## 十五、已知边界与后续

1. **`members.coupons` 列仍在**：展示已改用券表真值，但管理端会员编辑表单仍在写这一列。
   下次改会员表单时一并移除该字段，避免运营误以为能手工发券。
2. **多实例部署**：领取依赖数据库唯一索引，天然跨进程安全；核销依赖条件更新，也安全。
   但 `OrderService.create` 的取号仍是单实例 `synchronized`（历史遗留），与券无关。
3. **券不可转赠、不可拆分**：面额固定，不做「部分使用」。若将来要支持，
   `discount_amount` 列已预留「实际抵扣」语义，但需要新增余额列与多次核销的状态机。
4. **不做自动推送**：周一自动提醒需要订阅消息模板与用户授权，属独立议题。
5. **`gift_type=DRINK` 的生日赠饮**仍未开放，若要落地可复用本表的「面额型券」模型，
   把 `min_spend` 设为 0、`amount` 设为赠饮单价。
